# 仓库迁移重构全流程（方案 → 审计 → 裁决 → 实施 → e2e → 核销）

本 skill 沉淀自多次「单体服务仓库 → 分层新架构」迁移实战。核心信念：
**旧代码的行为（含旧测试）是唯一规格；文档与代码同步演进；测试门禁只许补齐不许放水；
e2e 的价值不在绿，而在抓出单测永远够不到的接缝缺陷。**

## 0. 先定位阶段

迁移是一个带状态机的流水线。用户找你时可能处于任意一环，先判断再动手：

```
方案先行 → 旧实现审计 → 逐模块裁决 → 测试计划 → 分阶段实施 → e2e 补齐 → 收口核销
 草稿      审计中       定稿         定稿      实施中      独立切片     已核销
```

判断依据：仓库里是否已有设计/实施/迁移文档及其状态标注。没有文档 = 必须从第一阶段开始
（不存在「直接搬代码」的合法入口）。若已有文档但与代码冲突，先改文档再改代码。

**中途接入**（迁移做了一半才引入本流程）：已迁但无文档的代码按「待审计」处理——
用同样的审计标准对已迁代码回补裁决表与迁移矩阵（旧实现行为仍是对照基准），
补完档再继续推进；不允许「已写的代码免检、只管后面」。

## 1. 需求澄清（不确定时主动问——用 ask 工具，不猜）

迁移全程的裁决点遇到不确定/逻辑模糊，**必须问用户，禁止猜一个方向闷头做**：

- **外部契约形态**：新架构的契约有多个合理候选（参数形状、错误形态、事件时序）；
- **规格冲突**：旧实现行为、旧文档、旧断言三者矛盾——**哪边是规格**是方向性
  裁决，不许默默选边；
- **裁决边界**：逐模块裁决表里 复制 vs 重写 vs 不移植 拿不准（通常意味着审计
  证据不足——先补审计，仍模糊再问）；
- **「不处理」归属**：设计的问题域边界不知道归属哪个消费方；
- **挂账取舍**：某缺陷/用例当波修掉还是挂账后续波次。

**先自查再问**：旧代码/旧测试能读出答案的先审计（旧代码的行为是唯一规格，
大多数问题靠读码解决）；已有「用户裁决」可引用的直接引用。
迁移项目的澄清成本高（答错返工的是成片代码），宁问勿猜。

**怎么问**：用 AskUserQuestion 工具（选项式提问），不要在长文本里连环追问：

- 每个问题 2-4 个**具体**的选项（各自的取舍/后果写进 description）：分叉互斥
  用单选，**可合法共存的叠加形态用 multiSelect**（推荐组合仍标 (Recommended)）；
- 一次调用可批量 1-4 个问题——攒齐一次问；**依赖式二轮提问合法**：仅当新分叉
  确实由上一轮答案派生时发起，且同样攒批；
- 用户的选择落档为「用户裁决」进对应文档（DESIGN / MIGRATION），
  同一裁决只在一处定义；选「Other」的自定义答复同样落档。

## 2. 方案先行（动代码之前，文档定稿）

产出三件套（复杂度决定可以合并，但三块内容缺一不可）：

1. **DESIGN（设计基线，定稿后少改）**
   - 外部契约：API 形态、事件时序契约、参数与结果的结构约定；
   - 内部问题域：处理什么 / **明确不处理什么**（不处理的写清归属哪个消费方，不留白）；
   - 并发与性能预算：数字化硬约束（每帧同步耗时量级、每连接内存量级、全局定时器个数等）。
   - 每个方向性裁决标注「用户裁决」落档。
2. **IMPLEMENTATION（施工图）**：审计结论、逐模块裁决表、拆分决策、测试计划、实施顺序。
3. **MIGRATION（每个迁移单元一份）**：行为规格基线（旧测试清单）、逐模块裁决、
   API 新旧对照表、测试迁移矩阵、回滚方案、验收清单。

**三件的定稿时点交错**：DESIGN 可以基于读旧码先出草稿；IMPLEMENTATION 与
MIGRATION 的裁决内容必须等审计证据（见 §3）才能定稿。实际顺序：
DESIGN 草稿 → 旧实现审计 → 裁决表 → 三件定稿。

模板与产出物细则见 `references/documents.md`。

## 3. 旧实现全量审计（有旧代码时，不可跳过）

逐文件过四条标准，产出三个清单：

- **四条标准**：① 正确性（边界、错误路径、静默吞错）② 契约符合（无隐藏默认、
  无跨请求状态、无策略数据混入机制层）③ 实现质量（职责单一、无重复、热路径预算）
  ④ 依赖方向干净。
- **三个产出**：真 bug 清单（编号 + 位置 + 级别，计费/数据丢失优先）、重复代码清单
  （提取计划）、契约缺口（演进决策）。
- 诚实区分「实测确认」与「待审计」。可以并行委派审计，但裁决必须基于证据。

细则见 `references/audit.md`。

## 4. 逐模块裁决

每个旧文件一行：**复制 / 复制+微修 / 重构 / 重写 / 不移植**，附审计状态列。
复制的前提是审计无可挑剔；审计发现问题就升级裁决并回写表格。「不移植」的项要在
迁移文档显式挂账并说明后果（推迟 ≠ 缺失）。

## 5. 测试计划先行

- **旧测试 = 行为规格**：迁移矩阵逐条标注 移植 / 改写 / 删除+理由；
- **每个真 bug 一个回归用例**，用例名注明编号与症状；
- 必测清单：契约级（词表封闭性、事件时序、判别联合穷举）、边界与异常（零值/超大/
  取消/超时/竞态）、表驱动（错误码表、参数矩阵）；
- 覆盖率阈值写进门禁；未达标只许补测试，**禁止调低阈值换绿**；提交时如实报告数字。

## 6. 分阶段实施

- 每阶段独立提交、可独立回滚；提交信息引用文档节号，保证可追溯；
- **四门**：typecheck / lint（0-0）/ build / test 全绿才算阶段完成；
- 实现中发现文档有误：同一提交内先改文档再改代码，禁止口头漂移。

## 7. e2e 补齐（独立切片，验收的硬指标）

e2e 的目标是「跨进程、跨真实中间件、穿过全部接缝」的旅程验证。建造要点：

1. **隔离世界装置（kit）**：每文件独占一个隔离数据区（如独立 schema：全量建表链回放，
   对跨链引用的缺表错误按错误码白名单容忍），结束整体销毁——不需要对共享环境做
   快照/还原/逐表清理；
2. **脚本化外部依赖替身**：对第三方上游/服务做本地脚本化 server（协议兼容、行为可
   编程、请求全量录制），覆盖全部向量（成功/失败/慢/挂起/畸形）；**真上游契约测试
   单列 opt-in 的 real 门**（花钱/要凭证的不进默认门禁）；
3. **全真装配**：被测系统用与生产同款的装配根启动（真数据库/缓存/计费），替身只替换
   「网络对端」，不替换内部层——否则测不到接缝；
4. **种子事实沿用旧断言口径**：把旧测试依赖的共享环境事实（价格、目录名、渠道参数）
   变成显式种子数据，**断言值零漂移**；旧硬编码 id 改为断言世界种子值，并在文档
   记录为装置适配；
5. **资金/状态对账工具**：台账式 helper（发凭证、充值/落账、驱动后台结算直到收敛、
   强对账断言：总量守恒 + 在途归零）；
6. **断言语义逐条等价，装置适配全部记录**：线名归一、旋钮语义映射（如「建连超时」
   在新架构改为「总预算超时」）、因内部机制变化而调整的请求形态（如流式消费从
   主动泵送变为按需拉取时，攻击向量改为「读完全部再断」）——每一条都在迁移文档
   列名，不许静默改断言；
7. **双形态进程冒烟**：源码运行形态与构建产物形态各起一个真实进程，验证
   探针/鉴权/一次全链请求/优雅停机退出码，数据自清；放进可重复执行的默认门；
8. **运行装置**：根级脚本入口（默认门 / real 门 / 冒烟单入口）+ README 说明依赖解析
   方式（e2e 不是包时，用符号链接借最近一个包的依赖闭包是常用解法）。

装置建造与迁移对照的细则见 `references/e2e-harness.md`。

## 8. 集成缺陷定位纪律（e2e 抓到问题时）

e2e 挂了是**资产不是麻烦**。定位纪律：

1. **逐层二分**：HTTP 入口 → 应用编排 → 能力包 → 依赖库，每层用最小直接调用验证
   （绕过上层直调下层），锁定挂起/失败发生在哪一层；
2. **微复现优先于源码阅读**：怀疑运行时/平台语义时，写 10-30 行独立复现脚本在
   裸运行时验证（不 import 任何业务代码），区分「平台语义如此」与「我们的组合用错了」；
3. **警惕的平台语义坑**（都是真实踩过、且各运行时行为可能不一致）：
   - 流式管道的**需求耦合**：变换流的 transform 回调可能只在下游有人读时才执行——
     「等首个事件再返回流」的结构会自锁；
   - **tee 分支取消**：流分叉后取消单个分支可能不 resolve，且会卡住另一分支的管道；
   - 连接池/资源上限在并发负载下的排队与超时（表现为随机 5xx）；
   - 打包产物缺静态资产、运行条件（development/production）改变模块解析目标；
4. 修复后：**修复所在包的全部既有测试回归 + 在迁移文档登记缺陷与修法**；
5. 临时插桩（console 打点）必须逐行撤干净——格式化工具会折行，按标记字符串删
   而不是按行号删，删完 grep 验证。

详见 `references/debugging.md`。

## 9. 收口核销（全部满足才算完成）

- 四门全绿 + 覆盖率达标 + real 门通过 + e2e 默认门全绿 + 双形态冒烟通过；
- 迁移文档验收清单逐项打勾（行为对照逐条列出）；
- 挂账项逐条显式（不迁清单 + 理由 + 后果 + 归属后续波次）；
- 文档状态推进到「已核销」；如实报告所有数字与遗留项。

## 10. 全程纪律（违反 = 返工）

- **单一真相**：同一事实只在一处定义；缺省值只住在装配/配置层；
- **零兼容层**：不写双轨字段、旧路径别名；发现即删；
- **一动词一文件**：文件超行数指引先问是不是装了两件事（测试装置例外但也要按职责拆）；
- **任务连续到生产可用**：中途可汇报但不停顿；上下文受限时把状态提交进 git 可续；
- **并行开发是常态**：只提交自己点名的文件；共享产物混有他人未提交变更时不提交；
  别人的在途 lint/门禁失败如实标注归属，不越界代修；
- **错误 message 用中性语言**（如英文），本地化文案走目录机制，不在抛出点硬编码。
