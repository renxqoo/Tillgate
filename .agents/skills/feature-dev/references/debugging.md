# 集成缺陷定位纪律（挂起 / 接缝缺陷 / 无报错超时）

> 与迁移工作流共享同一套方法论（自包含副本，可独立使用）。
> 心法：症状是信号不是噪音——目标是把「无报错超时」变成一个
> **可命名、可微复现的根因**，修掉后留回归用例。

## 1. 先确认证据，再动手

- 挂起点在哪个 await / 哪一层？超时前有没有部分输出（响应头到了吗？
  下游服务收到请求了吗？副作用落库了吗？）；
- 三问切形态：「没发出去」（编排之前就挂）／「发了、对端回了、没人读」
  （流式自锁的典型指纹）／「发了、对端没回」（替身/配置问题）；
- **无报错超时的首选取证是挂起瞬间的调用栈转储**（解释器自带的栈打印/
  信号触发 dump，附在超时回调里触发亦可）——比加打点重跑更快；
- **单跑 vs 全量跑对比**：结果不一致本身就是证据（并发/顺序依赖、连接池、
  共享缓存键污染）；
- 缩短反馈环合法且推荐：单跑该用例、复现时临时收紧超时旋钮。
  **边界**：只影响本次定位运行、不进提交的收紧合法；门禁超时/覆盖率阈值
  调低换绿永远禁止。

## 2. 逐层二分

HTTP 入口 → 应用编排 → 能力模块 → 依赖库，每层写一个绕过上层直调下层的
最小用例。哪层从「正常」变「挂起」，界就在哪。

## 3. 微复现优先于源码通读

怀疑平台/运行时语义时，写 10-30 行、不 import 任何业务代码的裸运行时脚本
验证组合本身。**多运行时交叉验证**（不同版本解释器跑同一脚本）区分
「平台一致语义（我们用错了）」与「特定版本回归（升级/绕开）」。

注意：微复现自己也要写对——例如流管道的输出端没人消费时，搬运不完成是
**正确行为**（背压），不是缺陷。先排除测试自身的误解。

## 4. 平台坑清单（新功能集成最常见，逐项核查）

- **流式需求耦合自锁**：变换流的 transform 回调可能只在下游有人读时才执行。
  「等首个事件再返回流」的结构会互等成死锁——症状是客户端永远拿不到响应头、
  全程无报错。修法方向：上游首字节已被预读确认时事件即刻合成发出；一次性
  事件做幂等缓冲 + 晚订阅重放。
- **流分叉（tee）取消语义**：分叉后取消单分支可能长期不 resolve，还会卡住
  另一分支的管道搬运。修法方向：预读用原始 reader 直读 + 回放式包装流。
- **连接池/资源上限**：并发负载下随机 5xx、连接超时——先对齐池上限与
  负载预期，而不是调小并发掩耳盗铃。
- **模块解析条件**：development/production 条件改变依赖目标（源码 vs 构建
  产物）；子进程与测试宿主行为不同先查这个；构建产物缺静态资产（JSON 等）
  会让产物形态必挂——构建脚本补资产拷贝。
- **开发依赖解析差异**：日志美化器等只在开发形态用的依赖，子进程/产物形态
  可能解析不到——按形态补齐依赖声明。

## 5. 修复与回归

- 修复落点在哪层修哪层；动到别人在途的文件时改最小面、提交只点名自己路径；
- 修复所在模块的**全部既有测试**回归一遍；
- 补一条能反复暴露该缺陷的用例（它当初怎么挂的，就让用例怎么站着）；
- 临时插桩按标记字符串删（防格式化工具折行导致清理残留），删完全文 grep
  验证零残留。
