# 新功能开发工作流（分级 → 方案 → 测试口径 → 实现 → 四门 → e2e → 收口）

核心信念：**方案先于代码，测试口径先于实现，门禁只许补齐不许放水；
「代码写完了」不算完——过门 + 验收清单逐项 + 生产可用才算完。**

## 0. 先分级（决定后续重量，30 秒内完成）

| 级 | 判据 | 方案重量 |
| --- | --- | --- |
| **小** | 纯加法、1-2 个文件、无新外部契约（或契约只是枚举加项） | 单份轻量方案（模板 A） |
| **中** | 跨模块、新子模块、外部契约新增/变形、涉及并发或数据一致性 | 方案 + 实施两节（模板 B） |
| **大** | 新子系统、跨应用、架构性变化 | 完整方案三件套——并考虑是否该按迁移方法论走（repo-migration-e2e） |

分级判据四问：外部契约变不变？跨几层？有没有并发/一致性/数据量级语义
（量级常常是同步/异步架构的分水岭）？有没有**不可逆的存量数据/契约变更**
（改运行中系统、回填数据、破坏性契约——有一条就至少中级，通常直接大级）？
（契约不变的内部横向增强——重试/缓存/超时——按「小」走，判据就是第一问答「不变」。）
拿不准就升一级——降级随时可以，返工不行。

**无论哪级：零方案直接写代码没有合法入口；方案未定稿不写实现。**
（小功能的方案可以只有十几行——重量分级正是为了让小功能不被仪式感拖死。
小级的最轻达成：展示方案与默认裁决 → 用户一句确认或否决窗口内推进，
**允许单轮「方案+实现」连续完成**，方案随实现同一提交落档。）

## 1. 需求澄清（不确定时主动问——用 ask 工具，不猜）

方案起草前/起草中，遇到以下情形**必须问用户，禁止自行猜测后闷头实现**：

- **需求语义模糊**：一句话需求存在多种合理理解，且不同理解会导致不同实现
  （「加个导出」——导全量还是导当前页？同步还是异步？几乎每句口语需求都这样）；
- **逻辑空白**：方案的「不处理」边界不知道归属哪个消费方；
- **方向性分叉**：分级判据四问里有拿不准的答案，或契约形态/数据量级/
  不可逆性存在多个候选。

**先自查再问**：代码库能读出答案的先探查（定稿前可自由读库）；项目惯例/
既有裁决可引用的按默认处理并落档，给否决窗口即可——把用户时间花在分叉上。

**怎么问**：用 AskUserQuestion 工具（选项式提问），不要在长文本里连环追问：

- 每个问题 2-4 个**具体**的选项（形态/量级/取舍，不要「好/不好」）：分叉互斥
  用单选，**可合法共存的叠加形态用 multiSelect**（推荐组合仍标 (Recommended)）；
- 一次调用可批量 1-4 个问题——攒齐一次问，不要挤牙膏式多轮打断；
  **依赖式二轮提问合法**：仅当新分叉确实由上一轮答案派生时发起，且同样攒批；
- 每个选项带一句 description 讲清含义或后果，让用户不用反问就能选；
- 用户的选择落档为「用户裁决」写进方案；选了「Other」的自定义答复同样落档；
- 分级结果按默认裁决落档 + 否决窗口（不单独占用一次提问）；用户选择导致
  升降级翻转时，更新方案并在文字里告知新级别与重量变化。

## 2. 方案先行（分级文档）

必含内容（小功能可极简，但缺一不可）：

1. **外部契约**：API 形态（参数平铺、结果判别联合、可选参数有缺省）、错误形态、
   事件/副作用时序；
2. **问题域**：处理什么 / **明确不处理什么**（不处理的写清归属，不留白——
   没写清的「不处理」迟早变成隐藏职责）；
3. **并发/一致性预算**（涉及时）：数字化硬约束（耗时量级、内存上界、定时器个数）；
4. **方向性裁决落档**：与用户确认过的取舍标注「用户裁决」。

按级别读对应模板（小 → `design-a.md`；中 → `design-b.md` 自足全文）。
定稿前可自由读代码库探查（契约形态依赖现状），但不写实现。

**大级：三件套 + 借件裁决**（不另设模板文件——判据在主文档，结构按
repo-migration-e2e 的三件套起草：设计基线 / 施工图 / 单元文档）：

- 借件 vs 整体转入：交付物是**新能力**（有意改行为语义也算，如隔离维度、
  权限改造）→ 主流程留在本工作流，**借**迁移方法论的文档结构、存量审计
  纪律、「装置适配逐条记录」，收口按本工作流清单 + 行为对照核销；
  交付物是**行为等价的新架构** → 整体转入迁移方法论的完整状态机。
  模糊判据：存量行为是「必须存续的不变量基线」而新语义叠加其上 = 借件；
  存量行为整体就是规格本身 = 迁移；
- 大级必做：存量面盘点先行（数据访问/缓存键/后台任务里的隐式全局状态
  最高危）；测试口径把「存量不变量基线」与「新规格」分开列；跨进程
  隔离/权限面按越权矩阵做安全回归。

**方案纪律（所有级别通用）**：

- 状态机 `草稿 → 定稿 → 已实施 → 已核销`；定稿后改动在提交说明里记录原因；
- 方案落仓库随代码提交——「提交引用节号」隐含它必须在库里，不落库的方案
  等于没写（小级的替代落点见 design-a.md：PR 正文/函数头注释同样满足）；
- 实现推翻方案：同一提交内先改文档再改代码，禁止口头漂移；
- 方向性取舍要么写明请用户确认（标注「用户裁决」），要么按项目既有裁决引用
  ——没有落档的裁决 = 未来扯皮的根；收口时验收清单全部打勾、状态推进到
  「已核销」、数字如实报告。

## 3. 测试计划先行（实现前定口径）

写实现之前先列出「这个功能怎么算对」：

- **契约级**：词表封闭性（导出枚举 == 文档词表）、判别联合穷举、事件时序
  （终态最后、一次性事件恰好一次）；
- **边界与异常**：零值/空/垃圾形状、超大与超长、取消路径全部触发方式、
  超时矩阵、竞态（并发交错、晚订阅）；
- **表驱动**：错误码表、参数矩阵用数据表遍历断言——新增表项自动获得覆盖；
- **回归**：开发中发现的每个 bug 一个回归用例，用例名注明症状。

细则与写法纪律见 `references/testing.md`。

## 4. 实现纪律

- **单一真相**：同一事实只定义一次，放最底层被依赖的包；可变值（开关/阈值/币种
  类语义）装配注入且必填，缺省值只住在配置层；
- **零兼容层**：不留旧路径别名、双轨字段、「新旧参数都收」；发现即删。
  准确语义：分阶段实施必然产生过渡态——过渡允许，**收口时必须单轨**
  （双轨字段删净、别名删净）；在线数据回填/双写过渡写进方案的「实施顺序」节；
- **一动词一文件**：文件超行数指引先问是不是装了两件事；
- **未实现 = bug**：不写「接口先行 / TODO 将来实现」的占位——要么实现完整，
  要么文档显式挂「待办」并写清后果；
- **错误 message 中性语言**（如英文），面向用户的文案走本地化目录，不在抛出点硬编码；
- **小步提交**：每步独立可回滚、四门全绿；提交信息引用方案节号（可追溯）。

## 5. 四门与覆盖率

- 四门：typecheck / lint（0 警告 0 错误）/ build / test——每步提交前全过；
  门禁集合按项目语言取等价物（无独立 typecheck 的语言用其编译/静态检查步骤），
  缺哪道补哪道，不许静默缺席；
- 新代码入库同阶段补对应测试；
- 覆盖率阈值进门禁；**未达标只许补测试，禁止调低阈值换绿**；
- 提交/汇报时如实报告用例数与覆盖率数字，禁止只报「门禁全绿」隐瞒数字。

## 6. 跨进程旅程 → e2e 补充

功能横跨进程边界或真实中间件（数据库/缓存/队列/外部服务）时，单测够不到接缝：

- **项目已有 e2e 装置**（隔离世界/替身/台账对账类 kit）：直接加旅程——
  种子事实走装置既有口径、替身脚本按需扩向量、断言验证业务终态（对账/一致性，
  不只是 200）；装置的运行入口（默认门/real 门）一并挂上；
- **没有装置**：建最小装置（隔离数据区 + 一个可编程替身 + 一个全链旅程），
  一次性投入换后续所有功能的复用；
- 需要真实凭证/花钱的场景走 opt-in 的 real 门，不进默认门禁；
- e2e 挂了是资产不是麻烦——定位纪律见 `references/debugging.md`。

## 7. 集成缺陷定位（挂起 / 接缝缺陷）

新功能最常见的翻车点在「单测全绿 + 集成一跑就挂」。纪律：
证据先行（三问定位）→ 逐层二分 → 微复现优先于源码通读 → 平台坑清单核查 →
修复后全量回归 + 回归用例入库。详见 `references/debugging.md`。

## 8. 收口（全部满足才算完成）

- 四门全绿 + 覆盖率达标 + （有跨进程面时）e2e 旅程全绿；
- 验收清单逐项核销：外部契约逐条、边界清单逐条、并发/一致性预算逐条；
- 如实报告：用例数、覆盖率数字、已知遗留项；
- **任务连续到生产可用**：中途可汇报进展，但汇报不是停止点；上下文受限时
  把可续状态提交进 git 并明确剩余清单。

## 9. 存量代码与新功能的交互

- 新功能踩到存量代码的缺陷：小缺陷当场修 + 回归用例 + 提交说明；大缺陷
  （需要独立裁决/可能改契约）登记挂账（位置/症状/影响），不静默绕过；
- 新功能替代某段存量实现：被替代段先按「旧实现」对待做一轮快速审计
  （正确性/契约符合/依赖方向三问），确认语义后再删——**不许盲删**；
- 新需求撞上既有能力包（在其上补面/延伸）：先读该能力的既有方案文档对齐
  裁决与口径，分级按**实际改动面**折算（不是按整个包的重量）；既有文档
  与现状冲突时先改文档。

## 10. 全程纪律

- 并行开发是常态：只提交自己点名的文件路径；共享产物混有他人未提交变更时
  不提交，留待协调；别人的在途门禁失败如实标注归属，不越界代修；
- 提交信息用约定式格式（如 Conventional Commits），正文引用方案文档节号。
