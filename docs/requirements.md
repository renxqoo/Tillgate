## 1. 项目定位

**对外提供 API 服务的 AI 中转站**：把多个大模型供应商的 API 收敛到统一入口，对外售卖 token 能力。

已确认的核心决策：

| 维度 | 决策 |
|---|---|
| 场景 | 对外提供 API 服务（商业售卖） |
| 核心功能 | 统一接口+多供应商、虚拟Key+配额、用量统计+计费、限流+熔断+重试 |
| 技术栈 | Bun（运行时与工具链，自 v1 的 Node.js 迁移而来，实测依据见 [benchmark-2026-08-21-bun-vs-node.md](./benchmark-2026-08-21-bun-vs-node.md)）+ Hono + Drizzle + Redis/BullMQ + PostgreSQL + OpenTelemetry（详见 tech-stack.md） |
| 规模 | 大规模 / 高并发（需水平扩展） |
| 用户体系 | 对接企业已有账号系统（OIDC 标准预留）+ 网关自签 Token 双凭证鉴权（见 4.2） |
| 计费模式 | 阶段一：充值余额按量扣费；阶段二：套餐订阅制 |
| 充值方式 | 充值码 / 卡密 |
| 管理员二次登录 | 邮箱验证码（默认关，设置页自助开；SMTP 未配置 fail-closed） |
| 用户面板登录 | 邮箱+密码 → **强制邮箱验证码两步**（60s 限发/账号，错 5 次作废；SMTP 未配置 fail-closed 503） |
| 用户自助注册 | 邮箱+密码 → 邮箱验证码两步 → 建号即登录（同 IP 5 次/小时限流；邮箱唯一索引兜底并发） |
| 第三方登录 | GitHub / Google OAuth（Authorization Code + state 双提交；find-or-create 按平台 id，不与本地邮箱账号自动合并；未配置即隐藏入口） |
| 显示名称 | 邮箱注册默认 `rx` + 6 位随机；GitHub/Google 直接用平台用户名（姓名 → login/邮箱前缀）；用户可自助修改（1-32 字符） |
| 免费模型限额 | 每用户每日 500 次（FREE_MODEL_DAILY_LIMIT 可配；0=不限） |
| 欠费策略 | 信用模型：可用额度 = 余额 + credit_limit − 在途预留；授权时原子校验，不足拒绝（402）。结算实扣可能短暂透支至 -credit_limit，不会无限负余额（信用额度由 wallet credit-line 承载，`packages/billing/src/application/wallet/credit-line.ts`） |
| 供应商（一期） | DeepSeek、OpenAI、MiniMax、GLM（智谱）、Qwen（通义）；协议族已支持 openai-compatible / anthropic / gemini / azure / bedrock / vertex（见 4.3） |
| 前端 | Next.js 最新稳定版（App Router + React 19 + TypeScript + shadcn/ui）统一控制台 |
| 部署 | 云服务器 Docker 部署（起步：Docker Compose + Redis + 关系型数据库） |

## 2. 角色与权限

```
超级管理员（系统运营方）
  ├─ 渠道/供应商管理、模型定价、充值码生成、用户管理、余额调账
  ├─ 查看全量用量报表、请求日志、系统状态
  └─ 可设置全局限流与开关

普通用户 / 企业（购买方）
  ├─ 登录（OIDC 对接企业已有账号系统，自助或管理员开通）
  ├─ 创建/管理自己的虚拟 Key（可设过期、限流上限、额度）
  ├─ 创建应用（App）：企业 Agent 用 client_id/client_secret 换取网关签发的短期 Token
  ├─ 兑换充值码、查看余额与消费明细
  └─ 查看自己账号的用量统计与请求日志
```

预留扩展：代理商/分销角色（二期再评估，不做进一期）。

## 3. 端到端请求链路（核心业务逻辑）

```
客户端(携带虚拟Key, OpenAI 格式请求)
  │
  ▼
① 鉴权：校验凭证（静态 Key 查库 / JWT 本地验签）——有效 / 未过期 / 未吊销 / 未冻结
  │      失败 → 401
  ▼
①.5 授权：PostgreSQL 事务按完整费用上界足额预扣；余额不足 → 402（不发往供应商）
  ▼
② 限流：Redis 计数器，按 Key / 用户 / 模型 / 全局维度检查
  │      超限 → 429（含 Retry-After）
  ▼
③ 模型路由：外部模型名 → 模型映射表 → 可选渠道列表
  │      未配置/被禁用 → 404/400
  ▼
④ 渠道选择：按权重/优先级从可用渠道中挑选
  │      全部不可用 → 503（渠道熔断中）
  ▼
⑤ 协议转换：OpenAI 格式 → 目标供应商格式（Anthropic/Gemini 等）
  │      国内 OpenAI 兼容供应商 → 直接透传
  ▼
⑥ 转发调用：上游 API（非流式 或 SSE 流式透传）
  │      失败 → 按策略重试下一个渠道 / 熔断标记
  ▼
⑦ 响应转换：目标供应商格式 → OpenAI 格式（流式则逐帧转换）
  ▼
⑧ 计量：严格解析供应商 usage（流式从流尾 usage 捕获）；缺失/非法按估算结算并留 estimated/estimateReason 留痕（2026-08-17 政策，uncertain 状态已删）
  │
  ▼
 ⑨ durable receipt → Worker：计算实际费用（官方价×系数快照）→ 与请求前授权 **对账结算**（扣除实际费用并释放未使用预留，见 4.7）
  │      Worker/队列中断可由 PostgreSQL 扫描恢复；实际用量越过授权预估则按实际金额结算（信用模型），仅无可信收据的越界转 dead 人工复核
  ▼
⑩ 写用量明细 + 请求日志（用户/Key/模型/渠道/tokens/费用/耗时/状态）
```

**要点**：
- 计费走**足额预留模式**：请求前（①.5）按可证明上界原子占用额度，完成后（⑨）按可信 usage 扣除实际费用并释放未使用预留；可用额度不足在请求前即拦截（402），不产生上游调用。
- 账户资金口径分离（wallet 双分录）：授权只记 wallet_authorizations 冻结（冻结口径 = in_flight），不产生结算腿；用户端只展示已结算余额并允许结算后延迟刷新，管理端展示已结算、处理中冻结和可用额度三项。
- 转发失败的重试发生在渠道层（换渠道），重试本身**不重复计费**——只有最终成功的调用计费，失败渠道仅记录渠道日志。
- 流式响应必须**完整透传完**才能拿到流尾 usage，结算事件在流结束后才产生。

## 4. 功能模块明细

### 4.1 身份与登录（对接企业已有账号系统）
- 控制台登录走 OIDC 标准（Authorization Code 流程），取 IdP 返回的 subject/email 作为用户唯一标识。
- 适配器可插拔：一期实现 OIDC 标准 + 本地账号兜底（**本地账号由管理员开通，非自助注册**），后续对接具体 IdP（企业微信/飞书/钉钉/LDAP 等）只加适配器；体验额度按身份源唯一判定，本地/OIDC 账号同样适用。
- 新用户首次登录自动注册，**自动赠送体验额度 ¥1**（按身份源唯一判定，防刷；封禁后重注册不重复送）。
- 用户状态：正常 / 封禁 / 注销。

### 4.2 调用鉴权（双凭证模型）
面向两种消费方提供两套凭证，**共用同一套限流/计量/计费链路**：

**凭证 A：静态虚拟 Key**
- 控制台手动创建，`Authorization: Bearer sk_xxx` 直接调用，适合脚本/个人/轻量接入。
- 属性：名称、过期时间（可选）、独立限流上限（可选，默认继承用户级/全局）、备注。
- 可吊销（吊销后立即失效——吊销/封禁/改限流时同步清理 Redis 鉴权缓存，保证即时生效），永不暴露上游供应商真实 Key。

**凭证 B：网关签发的短期 Token（企业 Agent 推荐）**
- 企业用户在控制台创建应用（App），获得 `client_id / client_secret`（secret 仅首次下发时展示，可轮换）。
- 调用 `POST /oauth/token`（OAuth2 client_credentials 两腿流程）换取 `access_token`（JWT，默认有效期 3600s，`JWT_TOKEN_TTL_SECONDS` 可配）。
- 调用 API 用 `Authorization: Bearer <JWT>`；网关本地验签，**无需回调企业 IdP**——企业服务登录接入一次后，后续调用由网关直接验证。
- JWT 载荷：`typ`、`sub`(账户)、`app_id`、`scope`（限定能力/模型，可选）、`iat`/`exp`（无 coefficient/jti）。
- 撤销方式：① **禁用 App** → 网关验签直查 DB，禁用即时生效，已签发 JWT 立即全部失效；② **轮换 client_secret 只防密钥泄漏，不撤销已签发 JWT**（JWT 由网关密钥签发，与 client_secret 无关）。
- 一期不做 refresh_token（client_credentials 可随时再换，无刷新必要）。

**统一鉴权链**：网关收到 Bearer → 按前缀区分（`sk_`=静态 Key 查库 / JWT=本地验签）→ 统一得到调用上下文 {账户、App、费率卡系数、限流维度} → 进入同一套 限流→路由→转发→计量→结算 链路。

**企业接入形态（一期都支持）**：
1. 企业 Agent 直接调用网关 API（标准 OAuth2 换 Token，推荐，零 SDK）
2. 个人/脚本直接用静态 Key

### 4.3 供应商与渠道
- **供应商**：OpenAI / Anthropic / Gemini / 国内各家（OpenAI 兼容）等，每个供应商有协议类型标识。
- **渠道** = 供应商 + 上游 API Key 的绑定，核心属性：
  - 所属供应商、上游模型白名单（可选）
  - 权重、优先级（路由选择依据）
  - 状态：启用 / 禁用 / 熔断（自动）/ 维护中
  - 健康检查：定时探测，连续失败 N 次自动熔断，恢复后自动启用
- **4xx 持续失败不熔断但告警**：模型被上游下架等场景（400/404）单独计数，10 次/小时 → 面板告警并提示人工介入（4xx 不计入熔断，避免误熔断正常渠道）
- **死凭据隔离**：渠道连续 401/403（含错误文本特征：invalid api key / 认证失败 等）→ 标记「凭据无效」+ 告警 + **停止路由**该渠道（人工更换上游 Key 后恢复）；死凭据不计入熔断计数（避免一个坏 Key 熔断整个 provider，也避免坏 Key 无限重试刷日志）
- 一个模型可挂多个渠道，实现负载均衡与故障切换。

### 4.4 模型管理与路由
- 模型映射表：`对外模型名 → 真实模型名 + 渠道列表`。
- 对外模型名可自定义别名（如 `gpt-4o` 可映射到任一渠道的真实模型）。
- 模型状态：上架 / 下架（下架后新请求拒绝，已发起的请求不受影响）。
- 模型分组（可选）：按组统一配置系数与限流（二期评估）。
- **快/慢通道（二期）**：同一真实模型可配置多个对外模型名（如 `deepseek-chat` / `deepseek-chat-batch`），配合费率卡按模型覆盖系数实现差异化定价。
- **fallback 模型链（配置启用，默认关闭）**：mapping 可配置 `fallback_models`（对外模型名数组），主模型所有渠道失败后按序降级；降级后按**实际模型**的官方价计费（usage_logs 记主模型名 + 实际模型）。
- **模型参数规则（参数抹平）**：透传为基底，规则驱动处理各家参数差异——`ignore`（删除不支持参数）/ `clamp`（钳制超限值）/ `map`（参数改名）/ `unknown`（未知参数默认透传）；provider profile 内置默认 + 模型级 param_rules 覆盖（运营可配），适配层执行并产出 param_adjustment 事件（详见 ai-package.md §7.6）。

### 4.5 协议适配
| 适配器 | 行为 | 一期状态 |
|---|---|---|
| OpenAI 兼容 | 请求/响应直接透传 | ✅ 一期五家供应商（DeepSeek/OpenAI/MiniMax/GLM/Qwen）均为 OpenAI 兼容，渠道表记各家 base_url + key 即可，零格式转换代码 |
| Anthropic | 请求/响应格式转换 + 流式转换 | 二期按需 |
| Gemini | 请求/响应格式转换 + 流式转换 | 二期按需 |

- 统一对外格式：OpenAI `/v1/chat/completions`（含 SSE 流式）、`/v1/embeddings`（一期透传，见 api-contract.md 2.5）与 `/v1/models`（列出可用模型）。
- **多模态（image/audio/file）输入按策略开放**：每个主模型及 fallback 都必须配置 `billing_policy`；一期只支持供应商把媒体成本纳入统一 `input_tokens` 的模型，并按模型硬输入上限足额授权。无策略、未知内容类型、非 HTTPS 远程媒体、非法 base64/MIME/detail/音频格式一律在预扣和上游调用前拒绝；音频输出及独立媒体价格模式尚未建立可证明上界时拒绝。
- **tools / tool_choice 透传支持**（企业 Agent 工具调用刚需，不在"未知参数忽略"范围内）。

### 4.6 限流
- 维度：凭证维（key:/app:/pg:）+ 用户维并罚；另有全局、模型维 TPM 与渠道维限流（渠道并罚）。
- 单位：RPM（请求数/分钟）、TPM（token 数/分钟）、QPS。
- **TPM 计量口径**：以历史已完成请求的可信供应商 usage + 本次请求输入/输出上限原子预占计算；完成后按可信实际 usage 修正。
- 实现：Redis 计数器（滑动窗口或令牌桶），超限返回 429。
- 渠道级熔断与限流（上游 429/5xx 反馈）单独处理，不与用户限流混淆。

### 4.7 计量与计费（阶段一：按量扣费）
- **定价模型（两层，核心）**：
  1. **官方价**：`model_mappings` 存官方价（输入价 / 输出价 / **缓存输入价**，每百万 token），按供应商官方定价配置，随官方调价更新；
  2. **费率卡系数**：平台定义多套费率卡（如「标准 1.0」「快速 1.5」「套餐A 0.8」），**账户绑定一张卡**；最终用户价 = 官方价 × 系数。系数即定价/利润空间，支持按模型/模型组覆盖（一期先做全局系数，按模型覆盖二期）。
  - **系数存储设计**：官方价与系数分离（官方调价只改官方价表，改套餐只改费率卡）；费率卡结构天然支持多套餐、快/慢通道；系数快照进 `usage_logs` 保证历史账单稳定。
- **缓存 token 计费（重要）**：
  - usage 中**缓存命中的输入 token**（OpenAI 风格 `prompt_tokens_details.cached_tokens`、DeepSeek 风格 `prompt_cache_hit_tokens`）按**缓存价**计费，与普通输入区分；
  - 计费公式：`(未缓存输入 × 输入价 + 缓存输入 × 缓存输入价 + 输出 × 输出价) / 1e6 × 系数`，全程 Decimal，不做展示精度式四舍五入；
  - 缓存输入价默认取官方价（DeepSeek = 输入价 10%、OpenAI = 25%，按官方配置）；缓存输出计价暂未启用（字段已预留）。
- **tokens 来源**：只接受供应商响应中的可信 usage（OpenAI `prompt/input_tokens`、DeepSeek `cache_hit+cache_miss` 等经严格归一化）。负数、小数、超安全整数、字段冲突、cached 大于 input、总量不一致或 usage 缺失都不得进入正常结算；字符估算只用于容量规划/TPM，不用于资金扣费。
- **计费时机（billing_requests 状态机）**：
  1. **请求前授权**：文本/JSON 输入按校准估算（estimateInputTokens + CJK 权重）计算 tokenizer 无关的保守 token 上界，输出按主模型与 fallback 最贵候选及完整输出上限计算；超过 BILLING_RESERVATION_MAX 则要求降低输出上限。默认 full 模式按完整风险预估冻结；显式 fixed 模式仅对纯 PAYG 冻结 BILLING_FIXED_RESERVATION_AMOUNT，但日限额仍按完整风险预估，最终实际用量全额结算并允许形成负余额；无法证明上界的多模态输入必须使用 provider 专用报价策略或拒绝；
  2. **结算对账**：请求完成后按报价内价格/系数快照和可信 usage 计算实际费用；`actual <= reserved` 才写 usage_logs + transactions，同时从已结算余额扣 actual 并释放完整预留；
  3. **越界结算**：有可信 usage 的越界按实际金额结算（信用模型允许短暂透支，地板为 -credit_limit）；无可信收据才转 `dead` 冻结预扣等待审计，禁止静默少扣；
  4. **故障恢复**：只有仍为 authorized、从未触达上游且授权过期的请求可 CAS 退款；in_flight 过期按估算结算留痕（uncertain 已删，2026-08-17 政策）。Worker 通过 DB claim/fence/heartbeat 重放，BullMQ 只负责低延迟唤醒。
  - 套餐用户（二期）：请求前优先预扣套餐额度（quota 同模式），不足且 fallback 开 → 预扣余额；结算按 4.9 判定。
- **结算告警（防静默亏钱）**：可计费但费用 = 0 且有 tokens → 「缺价格配置」告警；可计费但零用量且无错误 → 「usage 提取异常」告警；均进 OTel 指标 + 面板。
- **计量记录**：每次调用一条明细（用户、Key、模型、渠道、输入/缓存输入/输出 tokens、官方价与系数快照、**上游成本 upstream_cost（供应商对账数据基础）**、用户费用、耗时、状态、时间戳），长期保留用于对账与审计。

### 4.8 充值码（卡密）
- 管理员按批次生成充值码：面额、数量、有效期（可选）、备注。
- 兑换：用户输入充值码 → 校验有效性/未使用/未过期 → 余额增加 → 码标记已用（记录兑换人/时间）。
- 批次可查看：生成记录、兑换记录、剩余数量。
- 充值流水入账（收款记录），供对账。

### 4.9 套餐订阅（二期实现，一期建表预留）
- **套餐定义**：价格、周期（月/年）、**金额额度**（如 ¥100/月，按「官方价 × 系数」折算费用扣减，与按量同口径）。
- **覆盖范围**：套餐额度适用于全部上架模型（一期）。
- **计费判定（组织/成员模型，凭证绑定计费账户）**：
  1. 凭证（key / App）显式绑定 `subscription_id`（NULL=余额）。
  2. **绑定订阅**：扣该订阅额度（个人订阅，或所属组织订阅共享池）；额度尽 → 402；无有效订阅/无权 → 402。永不碰余额。
  3. **绑定余额**：只扣余额（含信用透支）；余额不足 → 402。
  4. 同一请求不混扣（`billed_by` 恒为 plan 或 payg，`both` 结构性删除）；套餐额度尽**不自动落余额**。
  5. 成员用量控制：共享池（额度×席位）+ 成员日限（a）+ 成员子配额（b），超限硬顶 402。
- **组织/席位**：团队套餐购买即建组织（owner 占 1 席）；席位 = 成员数 ≤ quantity（邀请接受事务 + 订阅行 FOR UPDATE 串行化）；拒绝降级；成员可多组织、换 key 即换来源。
- **购买与续费**：充值码 → 余额 → **余额购买套餐**（复用充值体系，一期闭环）；管理员可开通/续费/取消；在线支付购买二期。续费自动把旧订阅的凭证改绑到新订阅。
- **到期处理**：到期自动停用（剩余额度清零不可恢复）；续费开启新订阅期。
- 套餐可**绑定费率卡**（不同套餐享不同系数），与按量计费共用「官方价 × 系数」口径。

### 4.10 管理后台功能清单
**管理端**：
- 仪表盘：今日请求量、token 消耗、费用、成功率、渠道健康状态
- 用户管理：列表、封禁/解封、余额调账、费率卡绑定、手动开通
- 渠道管理：CRUD、批量导入、健康检查状态、熔断记录
- 模型管理：模型映射、官方单价配置（输入/输出/缓存输入）、上/下架
- 费率卡：费率卡 CRUD、系数配置、用户绑定查看
- 套餐与订阅：套餐 CRUD、订阅列表/开通/续费/取消
- 充值码：生成批次、查看兑换记录
- 报表：按时间/用户/Key/模型/渠道维度统计用量与费用；**展示时区 Asia/Shanghai**（存储仍 UTC）
- 请求日志：查询（时间/用户/Key/模型/状态），可看错误详情；摘要截断长度可配置（默认 2000 字符），管理员可凭 request_id 查询全文（受权限控制）

**用户面板**：
- 首页：余额、套餐剩余额度（如有）、今日用量、模型列表
- Key 管理：创建/吊销/限流设置
- 充值：输入充值码兑换、充值记录
- 用量明细：自己的消费记录与统计
- 模型列表：可用的对外模型名（来自 `/v1/models`）

## 5. 关键业务规则汇总（决策点）

| # | 决策点 | 已定方案 | 备注 |
|---|---|---|---|
| 5.1 | 计费时机 | 足额预留：请求前按上界原子占用额度，请求完成后按可信 usage 扣除实际费用并释放未使用预留 | durable receipt 先落 DB，Worker 异步结算 |
| 5.2 | 计费并发与坏账 | ✅ 足额授权 + durable receipt | 余额不足不上游；预付费实扣不超过授权，超额单独告警 |
| 5.3 | 余额不足 | 请求前按「余额+信用−在途」原子校验，不足拒绝（402） | 实扣可短暂透支至 -credit_limit（信用额度由 wallet credit-line 承载），不无限负余额 |
| 5.4 | 渠道重试计费 | 仅成功调用计费，失败渠道不计费 | 重试换渠道属于内部行为，用户无感 |
| 5.5 | 流式计量 | 从流尾 usage 捕获 | 无可信 usage 按估算结算留痕（estimated/estimateReason） |
| 5.6 | 估算策略 | ✅ 1 token ≈ 3.5 字符起步 | 估算用于请求前足额授权、TPM 预占，以及缺 usage 时的估算结算（estimated/estimateReason 留痕，2026-08-17 政策） |
| 5.7 | 货币与定价精度 | ✅ 元（人民币），内部 Decimal(38,18) | 前端统一截断展示 4 位，不四舍五入 |
| 5.8 | 请求日志保留 | ✅ 明细永久，请求体 30 天 | 按月分区滚动 |
| 5.12 | 缓存 token 计价 | 缓存命中输入按缓存价计（官方缓存价 × 费率卡系数） | usage 多格式归一化（见 4.7）；缓存输出计价未启用，字段已预留 |
| 5.13 | 定价模型 | 用户价 = 官方价 × 费率卡系数；官方价存 model_mappings，系数存 rate_cards，账户绑卡 | 套餐/快慢通道基于费率卡扩展（二期） |
| 5.14 | Key 类型分流计费 | 包月 Key 只扣订阅额度（额度尽/无订阅 → 402）；普通 Key 只扣余额（余额不足 → 402）；同一请求不混扣 | billed_by 恒为 plan 或 payg；见 4.9 |
| 5.15 | 空完成重试 | 200 但无内容（非流式空 choices / 流式零内容）→ 同渠道退避重试 ≤2 次，仍空换渠道 | 非流式在完整 body 收到后（尚未回给客户端）判定，与 5.9「响应未开始」一致 |
| 5.16 | 死凭据隔离 | 渠道连续 401/403 → 「凭据无效」状态 + 告警 + 停止路由；不计入熔断计数 | 坏 Key 不应熔断整个 provider，也不应无限重试刷日志 |
| 5.9 | 失败重试次数 | 最多尝试 3 个渠道；仅 5xx/429/超时/网络错误重试，4xx 不重试；**重试仅限响应未开始（首字节前）**——流已开始则直接断流透传错误，不再换渠道 | 可配置 |
| 5.10 | 熔断阈值 | 连续失败 5 次 / 上游 5xx 比例超阈值 | 可配置 |
| 5.11 | 流式中断计费 | 见下方「流式中断规则」 | 客户端断开与上游中断分别定义 |

**流式中断规则（5.11 展开）**：
- **客户端断开**（关页面/断网等）：网关主动断开上游连接；有供应商可信 usage 精确结算，否则按估算结算并留 estimated/estimateReason 留痕。
- **上游流中途失败**：若供应商返回可信 usage 则精确结算并标记 stream_aborted；缺少可信 usage 时按估算结算并留痕。
- **全程无输出**（首帧前失败）：不计费（status=1）。
- 字段定义见 `packages/db/src/schema/usage.ts`（usage_logs 注释）。

## 6. 技术架构（Docker 部署起步）

```
                    ┌─────────────────────────────────┐
  用户客户端 ─────▶ │  Nginx (TLS/反代/限流前置)        │
                    └───────────────┬─────────────────┘
                                    ▼
                    ┌─────────────────────────────────┐
                    │  Gateway 服务 (Bun, 无状态)      │
                    │  鉴权→预扣→限流→路由→转发→流式透传 │
                    │  多实例水平扩展                  │
                    └───────┬──────────────┬──────────┘
                            │              │
                    ┌───────▼───────┐  ┌───▼────────────┐
                    │ Redis         │  │ 计量队列        │
                    │ 限流计数       │  │ (BullMQ)       │
                    │ 熔断状态       │  └───┬────────────┘
                    └───────────────┘      │（仅唤醒）
                    ┌──────────────────────▼───────────┐
                    │ Worker (计量/结算)   │
                    │ DB claim→幂等结算→写明细│
                    └─────────────┬────────────────────┘
                                  ▼
                                 ┌─────────────────────┐
                                 │ PostgreSQL 16        │
                                 │ 用户/Key/渠道/模型/    │
                                 │ 余额/授权/收据/账单    │
                                 └─────────────────────┘
```

**Docker Compose 服务清单（详见 tech-stack.md 第 4 节；与 `docker/compose.yml` 一致）**：
| 服务 | 说明 |
|---|---|
| nginx | TLS 终止、静态资源、反代 gateway / client-api / admin-api / client / admin（certbot 负责证书签发与续期） |
| gateway | Bun 网关（对外 API + /oauth/token + 请求前预扣，无状态），可多副本 |
| client-api / admin-api | Bun 服务（用户控制台 / 管理控制面 REST API，无状态） |
| worker | Bun 计量/结算消费者（BullMQ） |
| trace-receiver | OTLP 接收部署单元（trace 落 PG，管理台「链路追踪」页查询） |
| client / admin | Next.js 前端（端用户面板 / 运营后台，两个独立部署） |
| migrate | 一次性 drizzle-kit 迁移 |
| redis | 限流/熔断状态/计量队列唤醒；不参与资金正确性 |
| postgres | 主存储（PostgreSQL 16） |
| otel-collector / prometheus / tempo / grafana | 观测栈（compose profile `obs`，默认关闭） |

**高并发关键设计**：
- Gateway 无状态 → K8s 化后只需加副本。
- 限流与熔断使用 Redis；资金授权使用 PostgreSQL 条件更新，余额不会因多副本并发超卖。
- Gateway 同步写入授权与不可变 receipt；BullMQ 丢失或 Worker 重启时由 DB 扫描恢复。
- Worker 用 `FOR UPDATE SKIP LOCKED`、claim lease、heartbeat 和 fencing CAS 多副本结算，事务内只生成一条 usage 与 consume 流水。

### 6.1 工程结构（v2：bun + turbo monorepo）

> 本节按 v2 目标结构改写，结构唯一权威为 [project-structure-refactoring.md](./project-structure-refactoring.md)。

- **7 个可部署应用（`apps/`，全部 private，永不发布）**：`gateway`（推理公网入口）、`worker`（后台任务/调度/结算恢复）、`client-api`（用户控制台 REST API）、`admin-api`（管理控制面 REST API）、`trace-receiver`（OTLP 接收部署单元）、`client`（Next.js 用户面板）、`admin`（Next.js 管理后台）。每个 app 的 `assembly.ts` 是唯一进程装配根。
- **14 个能力包（`packages/`，扁平 workspace）**：
  - 根契约与基础设施：`errors`（错误根契约）、`runtime`（配置/日志/Redis/加密/生命周期）、`db`（连接/schema/迁移）、`http`（纯 HTTP/Hono 基础工具）；
  - 业务能力：`identity`（凭据/挑战/MFA/OAuth/会话）、`accounts`（用户/组织/API Key/Application）、`billing`（**唯一资金与计费事实源**：money/wallet/ledger/rating/subscription/settlement）、`inference`（路由候选循环/quote/计费衔接/故障转移）、`control-plane`（管理员/供应商/渠道/模型/费率管理）、`notifications`（通知/outbox）、`ai`（零业务依赖的上游协议库：协议适配/透传中继/onEvent 观察面）；
  - 可观测：`observability`（OTel/trace/审计/请求日志）；
  - 外部产品候选：`api-client`、`ui`。
- **包内四层**：业务能力包基础方向为 `domain ← application`（业务规则只住 domain 纯函数，事务只住 application）；存在真实 I/O、外部服务或可替换实现边界时才增加 `ports ← adapters`，业务 SQL 只住 `adapters/postgres`，表定义只住 `db`。
- **v1 → v2 归并**：`wallet` + `ledger-core` + `money` + `service`（计费）收敛为 `billing`；`repository`/`domain`/`service` 按业务能力拆入各能力包的 `adapters/postgres`、`domain`、`application` 对应层；`core` 拆入 `runtime` + `http`；`identity-core` + `identity` 合并为 `identity`；`tracing` 改为 `observability`（完整映射见结构文档 §3.2）。
