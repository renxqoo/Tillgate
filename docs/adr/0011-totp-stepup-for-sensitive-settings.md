# ADR-0011：敏感设置操作的 TOTP step-up 认证

- 状态：已接受（2026-08-25，用户逐项裁决）
- 关联：`docs/integration-settings/DESIGN.md`（§4.1 写入面）、ADR-0008（动态 RBAC）

## 背景

集成设置（SMTP/OAuth/Turnstile/支付凭据）与登录形态开关（邮箱验证码二次登录）
是管理台最高危的写操作：篡改 SMTP 可截获二次登录邮件、篡改支付凭据直接影响资金。
管理员会话被劫持（XSS/设备失窃/会话固定）后，攻击者即可无声修改这些配置。
管理台已具备 TOTP 验证器（ADR 前置能力），但没有「操作时再验证」机制。

## 决策

敏感写操作强制 **TOTP step-up**（每次操作输入 6 位码，无时间窗）：

1. **强制点在服务端**：`PUT /v1/settings/integrations/:key`（7 个集成的
   配置/启用/停用共用）与 `POST /v1/me/two-factor` 请求体必填 `totpCode`，
   验证当前会话管理员的 TOTP；前端弹窗只是 UI 面，绕过 UI 直调 API 同样被拒。
2. **未绑定者一律拒绝**（403 + 错误信息引导先绑定验证器）：不做邮箱验证码
   替代（循环依赖：邮箱码依赖 SMTP，配 SMTP 本身需要 step-up）、不放行
   （fail-open 会被「挑未绑定账号打」绕过）。管理集成的资格 = 绑定 TOTP。
3. **每次输入，不做时间窗**：集成配置为低频操作，无状态实现最保守；
   将来需要 sudo 窗口时在验证通过点加许可缓存即可，不推翻本结构。
4. **防重放**：复用 identity `last_used_step` 单调 CAS（同 30 秒窗的码
   不可复用）；**step-up 只收 6 位 TOTP 码，不落恢复码分支**（恢复码留给
   紧急登录，日常操作不得消耗）——identity 提供仅 TOTP 的窄用例
   `mfa.verifyTotpOnly`。
5. **爆破防护与审计**：验证失败按登录面同口径计入守卫（IP 维度错次限速），
   失败与放行均写审计（复用 writeAudit）。
6. **TOTP 绑定/解绑不在 step-up 范围**：绑定前无码可验（鸡生蛋）；解绑
   维持现状自助（解绑本身要求有效验证码）。

## 已接受的残余风险（用户裁决记录）

- **全员解绑 = 敏感操作锁死**：解绑不做「最后守护者」限制——若所有管理员
  均解绑 TOTP，上述两端点永久无人可通过，需数据库级救援（清
  `identity_totp` 行，流程见 deployment-checklist）。
- 手机丢失且恢复码丢失同走数据库救援。

## V2 候选（本次不做）

渠道 CRUD（`channels.apiKeyEnc` 与集成密钥同类风险）、资金类操作（退款/关单/
调账）纳入同一 step-up 模式。

## 后果

- 新管理员引导顺序固定：先绑定 TOTP → 才能配置任何集成；存量未绑定管理员
  首次操作会收到引导性 403。
- 契约变更：两写端点请求体增加必填 `totpCode`（openapi/api-client 同步）。
- 管理台 UI：配置弹窗内嵌 TOTP 输入框；启/停与 2FA 开关先弹 TOTP 小窗；
  未绑定者相关按钮置灰并引导绑定。
