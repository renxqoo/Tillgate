# 01 · 存储引擎与数据组织（Storage Engine & Data Organization）

> 写 SQL 时你面对的是"表"和"行"；落到磁盘上，没有"表"这个实体，只有一叠固定大小的页（Page）、页内的槽位与字节布局。本篇讲清 InnoDB 与 PostgreSQL 在数据组织上的根本分歧（索引组织表 vs 堆表）、行与页的真实形状、页分裂与行迁移带来的写放大，以及主键设计为什么直接决定写入吞吐与存储成本——这是索引、MVCC、缓冲池等后续所有话题的地基。

## 读完本篇你应能回答

- PostgreSQL 堆表与 InnoDB 索引组织表的本质区别是什么？各自的主键索引叶子节点里存什么？
- 为什么页是数据库 I/O 的最小单位？InnoDB 16KB、PostgreSQL 8KB 对一行的存放意味着什么？
- NULL、长 VARCHAR/TEXT 在行内如何存储？溢出页与 TOAST 分别在什么条件下触发？
- 页分裂与行迁移各自在什么条件下发生？为什么随机主键会同时加重两者？
- 自增主键、随机 UUID、UUID v7/ULID 在写放大、页填充率、二级索引体积上差多少？

## 一、量级感先行：顺序 I/O 与随机 I/O

### 直觉

从书架上按顺序搬一排书很快；每本都跑去随机楼层取，即使单本速度一样，总时间也被"跑路"支配。数据库所有存储设计（B+ 树、预写日志（Write-Ahead Log, WAL））的原始动机，都是在用"顺序"换"随机"。

参考量级（用于建立直觉，具体数值随设备与队列深度变化）：

| 设备 | 顺序读吞吐 | 4KB 随机读 |
| --- | --- | --- |
| 7200 转机械盘（HDD） | ~100–200 MB/s | ~100–200 IOPS（≈0.4–0.8 MB/s） |
| SATA SSD | ~500 MB/s | 数万 IOPS |
| NVMe SSD | 3–7 GB/s | 十万到百万级 IOPS |

### 机制细节

- 机械盘上顺序与随机差约 3 个数量级（~200 MB/s vs ~0.8 MB/s）：随机访问要付 ~10ms 级的寻道与旋转代价，顺序读则把它摊薄到接近零。
- SSD 把鸿沟抹平了很多，但随机小 I/O 仍比顺序大 I/O 慢数倍（命令调度、内部写放大、GC），且需要高队列深度才跑得满。
- 结论：**减少随机页访问次数**（树更矮、页更满、插入更顺序）在任何介质上都是正收益；线上多是 SSD/云盘，可把"一次缓冲池未命中的页访问"粗记为 0.1ms 量级。

### 对开发者的实际影响

- 单条查询多几次随机页 I/O 通常无感；但每秒上万次写入、每次多一次页 I/O，就是每秒多上万次 0.1ms 级的访问——数量级的差异在写入路径上被放大。
- 后文反复出现的判断标准："这个设计让页访问更顺序、更少，还是更随机、更多？"

## 二、页：数据库 I/O 的最小单位

### 直觉

数据库不按"行"读写磁盘，而按"页"整取整存——像图书馆不借单页、只借整册。读 1 行也会把整页（几十到几百行）读进缓冲池（Buffer Pool）。

| 数据库 | 页大小 | 说明 |
| --- | --- | --- |
| MySQL InnoDB | 默认 16KB | `innodb_page_size` 可在初始化时设 4K/8K/16K/32K/64K（32K/64K 有功能限制），之后不可在线改 |
| PostgreSQL | 固定 8KB | 编译期常量，`SHOW block_size` 查看 |

### 结构：两种页布局

```text
(a) InnoDB 数据页（默认 16KB，页内自上而下）
+--------------------------------------------------+
| Fil Header 38B（页号、前后页指针、校验和）         |
| Page Header 56B（记录数、槽数、空闲空间指针）      |
| infimum / supremum（页内虚拟的最小/最大记录边界）  |
| 用户记录（向中间生长，按键值串成单向链）           |
|                ......空闲空间......               |
| Page Directory 槽（自页尾向前生长，页内二分入口）  |
| Fil Trailer 8B（校验和、日志序号）                |
+--------------------------------------------------+

(b) PostgreSQL 堆页（固定 8KB，两头向中间生长）
+--------------------------------------------------+
| PageHeader 24B（pd_lsn、pd_lower / pd_upper 等）  |
| 行指针数组 lp1, lp2, lp3 ...（每项 4B，向下生长） |
|                ......空闲空间......               |
| 元组数据 tuple3, tuple2, tuple1（向上生长）       |
| Special Space（堆页为空；索引页用它放页内目录）    |
+--------------------------------------------------+
元组标识符（Tuple Identifier, TID）= (页号, 行指针下标)，如 (7, 2) = 第 7 页第 2 槽
```

### 机制细节

- 两家殊途同归：**头 + 目录/槽 + 数据 + 尾**。InnoDB 的页内查找靠 Page Directory（每 4~8 条记录一个槽）：先二分定位槽，再在槽内小范围线性比对；PG 的堆访问由 TID 直接命中行指针槽位，它的 B+ 树索引页内部同样有目录可二分（02 篇）。共同点是先定位"槽"，绝不逐条翻页。
- InnoDB 页内的用户记录按键序串成单向链（next_record），物理位置可以任意；页与页之间用 Fil Header 里的前后指针串成双向链表——这是 02 篇范围扫描的物理基础。
- PG 的 `pd_lower` / `pd_upper` 标记行指针数组末端与元组数据起点，两者之间就是空闲空间。

```sql
-- MySQL 8.0：确认 InnoDB 页大小（默认 16384）
SHOW VARIABLES LIKE 'innodb_page_size';

-- PostgreSQL 16：页大小是编译期常量（默认 8192，即 8KB）
SHOW block_size;

-- PostgreSQL 16：用 pageinspect 直接"翻开"一页看内部（开发库执行）
CREATE EXTENSION IF NOT EXISTS pageinspect;
SELECT lp, t_ctid, t_xmin, t_xmax   -- 槽位、当前版本指针、事务号（04 篇展开）
FROM heap_page_items(get_raw_page('orders', 0))
LIMIT 5;
```

### 对开发者的实际影响

- 一行再小也要占一个槽位/指针；一行逼近或超过页大小，就必然走"外置存储"（溢出页 / TOAST，见第四节）——宽表不是免费的。
- 页越大，单次 I/O 摊到的行越多，范围扫描越省 I/O；但页分裂搬移的行更多、页内争用也更集中（08 篇展开）。这是默认值 16KB / 8KB 背后的权衡。

## 三、堆表与索引组织表：两种数据组织哲学

### 直觉

PG 把"书"和"目录"分开存：书按到的先后随手堆在仓库，目录卡片写着"第几排第几格"。InnoDB 直接按主键把整本书排进目录：翻开目录条目就是翻到书本身。

### 结构

```text
堆表（Heap Table，PostgreSQL）——数据无序，索引与数据分离，所有索引地位平等
   主键索引树           email 索引树          status 索引树
   叶子: id → TID       叶子: email → TID     叶子: status → TID
        ╲                    │                    ╱
         ╲────── 都平等地指向堆中的物理位置 ──────╱
                          ↓
   堆页: [(7,1)行] [(7,2)行] [(7,3)行] ...     ← 按插入先后堆放，无键序

索引组织表（Index-Organized Table, IOT，InnoDB）——表 = 主键 B+ 树（聚簇索引）
   二级索引 idx_email                     主键 B+ 树（即表本身）
   叶子: email → 主键值 ────回表────→ 叶子: 主键值 + 整行数据
   （没有独立"堆"，主键树的叶子就是表）
```

### 机制细节

- **PG**：INSERT 总是落到"任何有足够空闲空间的页"（由空闲空间映射（Free Space Map, FSM）引导）；每个索引（含主键）叶子都只存 TID（6 字节：4B 页号 + 2B 槽位）。PG 没有"聚簇索引"概念，`CLUSTER` 命令只能按某索引一次性重排整表，之后的写入不再维护该顺序。
- **InnoDB**：表本身就是主键 B+ 树，即聚簇索引（Clustered Index），叶子按主键序存整行；二级索引（Secondary Index）叶子存"索引列 + 主键值"，查完二级索引还要拿主键回主键树再找整行——这就是回表（Bookmark Lookup，详见 02 篇）。
- InnoDB 表没建主键时：取第一个"全列 NOT NULL 的唯一索引"充当聚簇索引；连这个也没有，就生成隐藏的 6 字节 `DB_ROW_ID`（全局共享计数器，不写入重做日志，别依赖它做任何逻辑）。
- PG 的堆组织是它的多版本实现（版本链放堆内，04 篇）的载体；InnoDB 的多版本则靠聚簇树内旧值 + undo 日志（回滚日志，记录修改前的旧值；04 篇）。表组织与 MVCC 设计是互相选择的。

| 维度 | 堆表（PostgreSQL） | 索引组织表（InnoDB） |
| --- | --- | --- |
| 表与主键索引的关系 | 分离；主键索引只是又一个索引 | 表 = 主键 B+ 树，删不掉 |
| 主键索引叶子存什么 | TID（6B 物理位置） | 整行数据 |
| 二级索引叶子存什么 | TID | 主键值（查整行需回表） |
| 二级索引宽度是否受主键影响 | 否 | 是：每个二级索引每行都复制一份主键 |
| 按主键的范围扫描 | 索引有序，但堆访问可能随机跳页 | 叶子连续，天然顺序 I/O |
| 数据物理顺序 | 插入序（大体上） | 主键序 |

### 对开发者的实际影响

- InnoDB 主键每宽 1 字节，**所有**二级索引每行都宽 1 字节——主键尽量短这条规则在 InnoDB 上是乘法，在 PG 上不是。
- MySQL 无主键表在 row 格式复制下，从库应用行事件要靠全表扫描定位行（09 篇展开）：每张 InnoDB 表都显式建主键，是纪律不是偏好。

## 四、行格式：一行在页内长什么样

### 直觉

一行不是把列值简单拼接：为了表达"这列多长""这列是不是 NULL""这行刚被哪个事务改过"，行首要带一小段元数据；超长字段像超规行李——托运到别处，随身只留取件条。

### 结构

```text
InnoDB COMPACT / DYNAMIC 单行布局（简化）
+---------------------------------------------------------------+
| 变长字段长度列表（逆序，每个变长列 1~2B） | NULL 位图（每 8 个  |
| 可空列 1B） | 记录头 5B（含 next_record 链） | DB_ROW_ID? (6B) |
| DB_TRX_ID (6B) | DB_ROLL_PTR (7B) | 列数据                    |
+---------------------------------------------------------------+
  长变长列本页放不下时：
  COMPACT : [前 768B 留在页内] + 20B 指针 ────────→ 溢出页（Overflow Page）
  DYNAMIC : [仅 20B 指针] ───────────────────────→ 溢出页（整列外置）

PostgreSQL 元组（Tuple）：头 23B（t_xmin / t_xmax / t_ctid / infomask 等）
  + NULL 位图 + 列数据（8 字节对齐）
  整行约超 2KB 时启用 TOAST：先压缩，仍超则把最大字段切 ~2KB 块外置，行内留 18B 指针
```

### 机制细节

- **InnoDB**：8.0 默认行格式 DYNAMIC（5.7 默认 COMPACT）。COMPACT 行放不下时，长变长列（如大 TEXT）在页内保留前 768 字节 + 20 字节溢出指针；DYNAMIC 则整列移到溢出页、页内只留 20 字节指针——大字段场景 DYNAMIC 让每页能装下更多"行头"，热点页密度更高。放不下的判定是"逐个把最长的变长列外置，直到行能塞进页"。
- NULL 在 InnoDB 里只占 NULL 位图的 1 个 bit，不占列数据区；PG 的 NULL 占元组头位图 1 bit，但列间对齐仍按完整布局计算。
- **PG 的 TOAST（The Oversized-Attribute Storage Technique）**：整行超过约 2KB（TOAST_TUPLE_THRESHOLD = 2032B，即 8KB 页的 1/4）时，先对变长字段压缩，压缩后仍放不下才外置到 TOAST 表（`pg_toast` schema 下的独立表），行内只留 18 字节指针。所以 PG 的"大字段"默认是"压缩优先、外置兜底"。
- 行里那些额外字段不是累赘：`DB_TRX_ID` / `DB_ROLL_PTR` 与 PG 的 `t_xmin` / `t_xmax` / `t_ctid` 是 MVCC 与回滚的现场（04 篇），它们让"每行的固定开销"在两家里都至少有 20 字节上下。

```sql
-- MySQL 8.0：显式指定行格式（默认即 DYNAMIC）
CREATE TABLE note_body (
  id   BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  body TEXT NOT NULL,
  KEY idx_id (id)
) ENGINE = InnoDB ROW_FORMAT = DYNAMIC;

-- MySQL 8.0：查看实际行格式（information_schema 引擎表需 PROCESS 权限）
SELECT NAME, ROW_FORMAT FROM information_schema.INNODB_TABLES
WHERE NAME = 'mydb/note_body';

-- PostgreSQL 16：找出某表的 TOAST 表并对比堆 / TOAST / 索引体积
SELECT c.reltoastrelid::regclass AS toast_table
FROM pg_class c WHERE c.oid = 'note_body'::regclass;

SELECT pg_size_pretty(pg_relation_size('note_body'))     AS heap_size,
       pg_size_pretty(pg_relation_size(c.reltoastrelid)) AS toast_size,
       pg_size_pretty(pg_indexes_size('note_body'))      AS index_size
FROM pg_class c WHERE c.oid = 'note_body'::regclass;
```

| 长字段策略 | InnoDB COMPACT | InnoDB DYNAMIC | PostgreSQL TOAST |
| --- | --- | --- | --- |
| 触发条件 | 行放不下页 | 行放不下页 | 整行约超 2KB |
| 页内保留 | 前 768B + 20B 指针 | 20B 指针（整列外置） | 18B 指针 |
| 是否先压缩 | 否 | 否 | 是（压缩后仍超才外置） |
| 读回代价 | 每个溢出列至少一次额外页 I/O | 同左 | 每约 2KB 块一次页 I/O |

### 对开发者的实际影响

- `SELECT *` 会把 TEXT/大 VARCHAR 一并拖出——列表页只取需要的列，省的不只是网络，还有溢出页/TOAST 的额外 I/O。
- "行很小所以表就小"是错觉：行头 + 槽位 + 对齐 + 页填充率，让真实占用常显著高于"列宽之和 × 行数"（第六节给数字）。

## 五、页分裂与行迁移：写放大的两个来源

### 直觉

页是固定大小的格子。InnoDB 往满页的中间插一行，得搬一半记录去新页（页分裂，Page Split）；PG 把某行更新得更大、本页放不下，整行搬去新页、原地留路标（行迁移，Row Migration）。

### 结构

```text
(a) InnoDB 页分裂：满页 A 中间插入 42 → 中点分裂
  分裂前:  ... ⇄ [页A: 10,20,30,40,50,60,70,80] ⇄ ...
  分裂后:  ... ⇄ [页A: 10,20,30,40] ⇄ [页C: 42,50,60,70,80] ⇄ ...
                                 ↑ 父节点新增目录项；两页各约半满
  对比：顺序追加（自增键）时新页只装新记录，老页保持近满

(b) PG 行迁移：UPDATE 使行变大、本页无空闲空间
  页100: [旧版本 t_ctid=(102,1)]   ← 所有索引仍指向 (100, 5) 这个 TID
                ↓ 跳转
  页102: [新版本（放大后的整行）]
  经索引读这行 = 页100 + 页102 两次页访问
  HOT 特例：新版本放得进本页空闲空间，且没改任何被索引列
           → 索引零维护，新旧版本在页内用 t_ctid 串联
```

### 机制细节

- **InnoDB 分裂**：随机插入在页中间触发中点分裂，两页各留一半；长期随机插入的 B+ 树页填充率收敛在 ~69% 附近（ln 2，经典结论），而顺序/批量插入可达 15/16（InnoDB 在顺序插入时按 15/16 填充、预留 1/16 空隙，为后续插入和页分裂留余量）。分裂一次要改两个页、更新父节点目录项和前后页指针——一次 INSERT 变成多次页写与 redo log（重做日志，即 InnoDB 的 WAL，用于崩溃后重放修改）。反向操作是页合并（相邻页删除后低于 MERGE_THRESHOLD，默认 50% 时归并）。
- **PG 行迁移**：旧元组的 `t_ctid` 指向新位置，索引不改——代价是每次经索引读这行都多一次页访问，直到 VACUUM 清理（04 篇）。
- **PG 的 HOT（Heap-Only Tuple）更新**：条件是"本次更新没改任何被索引列 + 新版本能放进本页空闲空间"。命中则索引完全不用动，这是 PG 更新密集表的生命线。
- 两者共同的推论：**写放大不是均匀分布的**——它由"插入位置是否随机、更新是否变大、索引是否被涉及"三个开关决定，而主键设计控制第一个开关（下一节）。

```sql
-- PostgreSQL 16：高频更新表预留页内空间，提高 HOT 命中、减少行迁移
--（fillfactor 默认 100；只影响之后写入的页，已有页需重建/VACUUM FULL 才重排）
ALTER TABLE events SET (fillfactor = 80);

-- PostgreSQL 16：查看死元组与页内空闲比例（pgstattuple 需相应权限）
CREATE EXTENSION IF NOT EXISTS pgstattuple;
SELECT dead_tuple_percent, free_percent FROM pgstattuple('events');

-- MySQL 8.0：粗估页填充率（TABLE_ROWS 是估算值，看量级即可）
SELECT TABLE_NAME,
       ROUND(DATA_LENGTH / 16384) AS leaf_pages,
       ROUND(TABLE_ROWS / NULLIF(DATA_LENGTH / 16384, 0), 1) AS rows_per_page
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'mydb' AND TABLE_NAME = 'orders';
-- 顺序插入的表 rows_per_page 常见 13~16；长期随机插入常见 8~11
```

### 对开发者的实际影响

- PG 更新密集表（状态机、计数器、last_seen 之类）主动设 `fillfactor 70~90`，给 HOT 留空间；同时少建索引——索引越多，"没改被索引列"越难成立。
- InnoDB 的对应手段是主键选顺序值（下一节），以及监控 `rows_per_page` 类指标发现页稀疏化。

## 六、主键设计：一个决定写放大与空间的选择

### 直觉

主键在 InnoDB 里不只是唯一约束，它是整张表的物理排序键。选递增键等于总在最后一页追加；选随机 UUID 等于每次都往随机位置插一行。

| 维度 | 自增 BIGINT | UUID v4（随机） | UUID v7 / ULID（时间有序） |
| --- | --- | --- | --- |
| 宽度 | 8B | 16B（存成 CHAR(36) 则 36B+，更糟） | 16B |
| 插入位置 | 最右页追加 | 随机叶页 | 近似最右追加 |
| 页分裂 | 尾部分裂，老页近满 | 频繁中点分裂 | 接近自增 |
| 长期页填充率 | 可达 ~15/16 | 收敛在 ~69% 上下 | 接近自增 |
| 大表缓冲池命中 | 热点集中在最右少数页 | 写穿缓冲池，命中率下降 | 接近自增 |
| 二级索引体积 | 每行复制 8B | 每行复制 16B，全部索引变大 | 同为 16B |
| 业务特性 | 暴露计数、分库需改造 | 全局唯一、可离线生成 | 全局唯一且有序 |

### 机制细节

- 随机主键的代价是一条链：中点分裂频繁 → 页填充率从 ~94% 掉到 ~69%（同样的行数多出 ~36% 的页）→ 树更容易再长高一层、缓冲池能缓存的有效行更少 → 读也跟着变慢。
- 16B 的 UUID 主键还让**每个**二级索引每行多背 8B（对照 BIGINT）；一张千万行、5 个二级索引的表，仅此一项就多约 400MB。
- 有序替代：UUID v7 / ULID 把时间戳放在最高位，保证同一毫秒内生成的 ID 单调递增。MySQL 8.0 可用 `UUID_TO_BIN(uuid, 1)` 把 UUID 的时间相关字节换到前面再存 `BINARY(16)`；PG 16 没有内置 uuidv7 函数，需应用侧或扩展生成（PostgreSQL 18 起内置 `uuidv7()`）。
- 顺带钉住两个版本行为：MySQL 8.0 起自增计数器持久化，重启不再回退（8.0 之前重启后按 `MAX(id)+1` 重算，可能重用已删的顶端值）；PG 的 sequence 从不回退，事务回滚产生的空洞也不回收——自增列当唯一标识没问题，当"无洞计数"不行。

```sql
-- MySQL 8.0：有序存储 UUID 的正规姿势（swap=1 重排时间字节，插入近似有序）
INSERT INTO t (id) VALUES (UUID_TO_BIN(UUID(), 1));
SELECT BIN_TO_UUID(id, 1) FROM t LIMIT 1;
```

### 对开发者的实际影响

- 新表默认 `BIGINT AUTO_INCREMENT` 或应用生成的有序 ID（UUID v7 / ULID / 雪花）；除非表小、写入低频，否则别拿 UUID v4 当聚簇主键。
- 已经用随机 UUID 的存量表：不要为此贸然改主键（重建成本与外键/复制风险都高），优先算清收益再动（11 篇的变更方法论）。

## 七、文件与表空间：磁盘上到底放了什么（点到为止）

### 机制细节

- **MySQL 8.0**：`innodb_file_per_table` 默认 ON，每张 InnoDB 表一个独立 `.ibd` 文件（表空间，Tablespace）；另有系统表空间 `ibdata1`、独立 undo 表空间、临时表空间与重做日志文件。独立 .ibd 让"单表空间可观测、可 `OPTIMIZE TABLE` 重建、可传输"成为可能。
- **PostgreSQL**：每个关系存放在 `base/<数据库OID>/<filenode>`；同一 filenode 至多三套文件（fork）：主数据文件（无后缀）、`_fsm`（空闲空间）、`_vm`（可见性映射，VACUUM 与索引扫描用它跳页，04 篇）；单文件超 1GB 分段（`filenode.1`、`filenode.2`…）；TOAST 表单独放在 `pg_toast` schema 下。

```sql
-- PostgreSQL 16：定位某关系的物理文件
SELECT pg_relation_filepath('orders');   -- 形如 base/16401/24587
-- 同一关系还有 24587_fsm、24587_vm；超 1GB 会出现 24587.1 等分段
```

### 对开发者的实际影响

- 看到 MySQL 的 `.ibd` 文件远大于 `DATA_LENGTH`，或 PG 的 `pgstattuple` 显示死元组比例高，都是"页稀疏/死元组多"的信号，结合第五节的指标判断是否需要重建。
- 物理布局决定备份工具形态（物理备份拷文件、逻辑备份导 SQL），15 篇展开。

## 开发者清单

**该做：**

- 每张 InnoDB 表显式声明主键，优先 BIGINT 自增或有序 ID（UUID v7/ULID/雪花）——避免隐藏 `DB_ROW_ID`、避免 row 复制从库全表扫、避免随机写放大三连。
- 主键尽量短——InnoDB 每个二级索引叶子都复制一份主键，宽度是乘法关系。
- UUID 用 `BINARY(16)` 存（MySQL 配合 `UUID_TO_BIN(id, 1)`）——宽度比 `CHAR(36)` 省一半以上，还顺带获得时间局部性。
- PG 更新密集表设 `fillfactor 70~90`——给 HOT 更新留同页空间，索引维护与行迁移同时减少。
- 列表/详情查询只 SELECT 需要的列——避开 TEXT 与大 VARCHAR 的溢出页/TOAST 额外读。
- 意识到"行有固定开销"（InnoDB 隐式列 ~20B、PG 元组头 23B + 对齐 + 行指针 4B）——大量小列窄表的真实体积要按页估算，不是按列宽求和。

**不该做：**

- 不要拿 UUID v4 这类随机值当 InnoDB 聚簇主键（高频写大表）——中点分裂、页填充率掉到 ~69%、全部二级索引膨胀，三者同时发生。
- 不要建无主键表——InnoDB 用隐藏 row_id 兜底（复制与定位代价），PG 虽无此机制但逻辑复制也要求复制标识（09 篇）。
- 不要用 `VARCHAR(36)` 存 UUID——宽度约 2.25 倍于 `BINARY(16)`，且纯属浪费。
- 不要为了"以后可能用"把大字段塞进高频更新的行——每次更新整行重写（05/04 篇），大字段放大每一笔。
- 不要指望 `CLUSTER` 维持 PG 的物理顺序——它是一次性重排，随后的写入立刻恢复堆序。

## 常见误区

1. **"表就是按插入序排列的行数组。"** PG 堆大体按插入序但无任何保证；InnoDB 严格按主键序。没有 `ORDER BY` 的查询不承诺任何顺序——依赖结果集顺序的代码是埋雷。
2. **"加索引只是加个指针，表数据仍是独立一份。"** 对 PG 成立（索引与堆分离，叶子存 TID）；对 InnoDB，主键索引**就是**数据本身，二级索引叶子存的是主键副本而非物理指针——删主键索引这件事根本不存在。
3. **"NULL 一点空间都不占。"** 只对了一半：InnoDB 里 NULL 不占列数据区（只占位图 bit）；但 PG 的 NULL 占位图位并参与对齐布局；且可空列越多，位图与变长元数据越长。
4. **"自增 ID 重启后一定接着上次最大值。"** MySQL 8.0 已持久化自增计数器；8.0 之前的版本重启后按 `MAX+1` 重算，可能重用已删除的顶端值。PG 的 sequence 天然持久，但事务回滚的空洞永不回收——"自增列的值只能当标识，不能当计数"。
5. **"行小，所以表小。"** 行头、槽位、对齐与页填充率让真实占用常高出朴素估算 30%~50%；随机主键的稀疏页会再放大一截——容量规划要按"页"而不是按"列宽×行数"。
6. **"页分裂只在写入时疼。"** 分裂的后果是持久化的：同样行数占更多页 → 树高与扫描页数增加 → 缓冲池有效容量下降 → 读路径同样变慢。

## 自测题

1. PG 的 TID `(7, 2)` 两部分各指什么？更新导致行迁移后它指向谁？
   （第 7 页第 2 个行指针槽位；迁移后索引里的 TID 不变，旧元组的 `t_ctid` 指向新位置。）
2. InnoDB 二级索引 `idx_email` 的叶子节点里存了什么？
   （email 值 + 主键值 + 页内链指针；没有行数据，取整行需回表。）
3. 为什么"主键尽量短"在 InnoDB 比 PG 重要得多？
   （InnoDB 每个二级索引叶子都复制主键，N 个索引 × 每行 × 主键宽度；PG 索引与主键宽度无关。）
4. DYNAMIC 行格式下，一个 100KB 的 TEXT 在数据页里占多少？
   （20 字节溢出指针，整列在溢出页；COMPACT 则还要留前 768 字节在页内。）
5. PG 里什么样的 UPDATE 能走 HOT？不满足时最坏发生什么？
   （未修改任何被索引列，且新版本放得进本页空闲空间；不满足且本页无空间则行迁移，索引读多一次页访问。）
6. 估算：行 1KB、InnoDB 16KB 页、顺序插入（页填充 15/16），一页能放几行？
   （16KB × 15/16 ÷ 1KB ≈ 15 行。）
7. UUID v7 相对 v4 解决了什么，没解决什么？
   （解决插入随机性：时间前缀使写入近似顺序；没解决 16B 宽度，二级索引相对 BIGINT 仍每行多 8B。）
8. 用一句话解释"减少随机页访问"为什么在任何存储介质上都成立。
   （SSD 随机小 I/O 仍比顺序大 I/O 慢数倍，且页访问次数同时消耗缓冲池容量与 CPU——只是收益从机械盘的 3 个数量级缩小到数倍。）
