# 10 · 分布式事务与一致性（Distributed Transactions & Consistency）

> 单库事务的 ACID 由存储引擎一手包办；一旦数据跨库、跨服务、跨地域，原子提交、一致性语义、甚至主键怎么生成都要重新设计。本篇从 CAP 讲到 2PC 与 Raft 共识，再落到业务侧最常用的本地消息表（outbox）、事务消息、Saga 与幂等三件套，最后讲分布式 ID——帮你建立"按业务代价选一致性强度"的决策框架。

## 读完本篇你应能回答

- CAP 里 P 为什么必选？C 与 A 的取舍粒度是"整个系统"还是"单个请求路径"？
- 最终一致的"最终"靠什么收敛？单调读、读己之写分别解决什么问题？
- 2PC 两个阶段各做什么？它最致命的弱点是什么，3PC 为什么仍未解决？
- Raft 的多数派提交与 2PC 的协调者提交差在哪？为什么共识能让"决定"本身容错？
- 本地消息表（outbox）为什么能保证"业务落库"与"消息发出"不丢不漏？
- 分库分表后为什么不能用自增主键？雪花 ID 各段位是什么含义，时钟回拨怎么办？

## 一、CAP：分区是常态，取舍是逐请求的

### 直觉

一致性（Consistency, C）、可用性（Availability, A）、分区容错性（Partition tolerance, P）三个愿望最多同时满足两个；而网络分区（网络断成几块、节点互相失联）在分布式系统里不是意外而是日常，所以 **P 没得选**，实际可选的是——分区发生的那一刻，这个请求要 C 还是要 A。

### 机制细节

- **C**：这里指线性一致性（linearizability）——任何读都看不到"过去"，表现得像只有一份数据、所有操作全序排队。
- **A**：每个请求都能得到非错误响应。
- **P**：网络断成几块时系统仍能工作。
- 分区发生时：选 C 就要拒绝部分分区里的请求（不可用）；选 A 就允许各分区各自接受写（分区恢复后必须处理冲突，期间不一致）。

关键认知：**取舍的粒度是子系统、是请求路径，不是整个系统**。同一个系统里，下单扣库存可以选 CP（宁可拒绝下单，不能超卖），浏览数/点赞数可以选 AP（先记下来，稍后收敛）。工程上"这是 CP 系统"这类说法只是粗略画像。

### CP 与 AP 风格的典型样貌（概念层面）

- **CP 风格**：共识型存储（etcd/ZooKeeper 类）与多数派提交的数据库——分区时少数派一侧停止服务、拒绝写入，换"已确认的数据不丢不错"。行为特征是**宁可拒绝，不可出错**。
- **AP 风格**：多主异步复制的 Dynamo 系存储——分区时两侧都继续接受写，恢复后靠版本/时间戳裁决冲突（最后写入胜出，或交给应用合并）。行为特征是**先服务，再对账**。
- 真实系统多为混合体：核心账务路径 CP、边缘体验路径 AP——再次说明取舍是逐路径的，不是给整个系统贴标签。

### 对开发者的实际影响

每设计一条跨节点写路径，先回答一句："分区/超时时，这条路径宁可拒绝服务，还是宁可暂时不一致？"——这个问题没有默认答案，答案就是你的架构决策本身。

## 二、BASE 与最终一致性

### 直觉

BASE（Basically Available, Soft state, Eventually consistent）是 AP 路线的工程化表述：接受软状态（中间态可见），换取分区下的可用性，承诺**最终一致**。

"最终"的准确含义：**停止写入后，只要网络恢复正常，所有副本经过有限时间收敛到相同状态**——不承诺何时，只承诺收敛。收敛靠两个机制：

- **读修复**（read repair）：读多个副本时发现不一致，顺手把新值写回旧副本；
- **反熵**（anti-entropy）：后台任务定期对账副本差异并修复（可用 Merkle 树——一种用哈希快速对比两份数据差异的树结构——缩小比较范围）。

### 客户端一致性语义

副本收敛了，单个客户端的体验还取决于路由方式。常用语义速查：

| 语义 | 含义 | 常见实现 |
|---|---|---|
| 写后读（read-your-writes） | 自己写的自己立刻能读到 | 写后短时粘主库；显式等待回放（见 09 篇） |
| 单调读（monotonic reads） | 不会读到比上一次更旧的值 | 会话固定路由到同一副本；带版本协商 |
| 单调写 | 同一客户端的写保持顺序 | 会话固定路由到同一分片 |
| 前缀读（consistent prefix） | 因果相关的读不乱序 | 因果时间戳/会话令牌 |
| 线性一致（linearizability) | 全局单副本假象，实时序 | 共识协议 + 单点写者 |

注："常见实现"列速览——粘主库：写后短时把该客户端的读固定路由到主库；回放：等从库追平复制位点再返回；版本协商/因果时间戳：请求携带已见版本、服务端拒绝返回更旧数据；会话令牌：服务端下发的、记录该会话已见版本的凭据（机制见 09 篇）。

教训：单调读不是白送的——读写分离里"第一次读到新数据、第二次反而读到旧数据"（请求落到不同延迟的从库），就是没有单调读保证的典型症状。

## 三、2PC：协议标准，问题也标准

### 直觉

两阶段提交（Two-Phase Commit, 2PC）像先举手表决再统一行动：先问所有参与者"能不能提交"，全票通过才正式提交，有一票反对就全体放弃。

### 结构：时序图

```text
  成功路径                                失败路径（参与者 B 投反对票）
协调者      参与者A    参与者B          协调者      参与者A    参与者B
  │─phase1: prepare─▶│                │─prepare──▶│
  │        锁资源、写 prepare 日志       │◀─yes──────│
  │◀─yes─────────────│                │─prepare──────────▶│
  │─prepare──────────────────▶│        │◀─no──────────────│（锁定失败/校验不过）
  │◀─yes─────────────────────│         │ 写下"abort"决定并持久化
  │ 全部 yes → 写"commit"决定并持久化    │─abort────▶│ 回滚、释放锁
  │─phase2: commit──▶│ 提交、释放锁     │─abort──────────▶│ 回滚、释放锁
  │─commit───────────────────▶│ 提交、释放锁
```

### 机制细节

- **阶段一（prepare / 投票）**：参与者把变更落盘并锁住相关资源，回答 yes/no。回答 yes 之后它就"骑虎难下"——**必须持有锁等待最终决定**，无权单方面提交或回滚。
- **阶段二（commit / abort）**：协调者把决定**先写本地日志**再广播；参与者执行并释放锁。
- **三大弱点**：
  1. **协调者单点**：参与者全部投完 yes 之后、协调者广播决定之前宕机——所有参与者持锁无限期阻塞，只能等协调者恢复（或人工介入）；
  2. **分区下的不一致窗口**：决定消息部分送达时，一部分参与者已提交、另一部分还在持锁等待，外部观察者会看到中间态；
  3. **性能**：两轮 RPC + 协调者与参与者各自落盘 + prepare 到 commit 之间**全程持锁**；跨机房一轮 RTT 就是毫秒级起步，高并发下锁持有时间被放大。

XA 是数据库层面的 2PC 标准接口，两大库都支持：

```sql
-- MySQL 8.0：XA 两阶段语法
XA START 'xid';
UPDATE account SET balance = balance - 100 WHERE id = 1;
XA END 'xid';
XA PREPARE 'xid';   -- 阶段一：落盘并锁资源
-- ... 协调者决定后 ...
XA COMMIT 'xid';

-- PostgreSQL 16：等价语法
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;
PREPARE TRANSACTION 'xid';   -- 阶段一
COMMIT PREPARED 'xid';       -- 或 ROLLBACK PREPARED 'xid';
```

### 3PC 的改进与局限

3PC 把流程拆为 CanCommit（询问参与者能否提交）→ PreCommit（预执行并预写日志）→ DoCommit（正式提交），引入**参与者超时**：超时未收到决定时默认提交（PreCommit 之后），消除了"协调者死了参与者永久持锁"的阻塞。但网络分区下它仍不安全：协调者决定 abort 而消息只送达一部分参与者时，未收到消息的参与者超时**默认提交**——不一致依旧可能。教训：纯超时设计换不来分区下的正确性，**没有银弹**；真正的解法是把"决定权"本身做成容错的——这就引出共识。

## 四、共识协议：让"提交决定"本身容错

### 直觉

2PC 的病根是协调者说"听我的"然后自己死了。共识（Consensus）把决定交给**多数派**：只要多数节点活着，决定就能做出，且做出后不可被推翻。多数派思想：**2f+1 个节点容忍 f 个故障**——因为任意两个多数派必有交集，已确认的值不可能被"另一个多数派"覆盖。（这是崩溃故障模型；若节点还可能"撒谎"（拜占庭故障），需要 3f+1 节点与 PBFT 类协议，数据库内部复制通常假设节点诚实，不考虑恶意行为。）

### Raft 一页讲清

Raft 是工程界事实标准的共识协议（etcd、TiKV 等都在用），三件事：

- **任期（term）**：单调递增的逻辑时钟，每次领导者选举开启一个新任期；过期任期的消息一律无效。
- **领导者选举**：follower 一段时间收不到 leader 心跳就变成 candidate，term+1 并向全体拉票；获得**多数票**者当选 leader。日志不够新的 candidate 拿不到票——这保证新 leader 必然持有所有已提交日志。
- **日志复制**：

```text
客户端 ──写 entry(term=5)──▶ Leader        5 节点集群，多数派 = 3
                            │ ① 追加到本地日志（尚未 commit）
                            ├──AppendEntries(entry, term5)──▶ F1 ✔ 已持久化
                            ├──AppendEntries(entry, term5)──▶ F2 ✔ 已持久化
                            ├──AppendEntries(entry, term5)──▶ F3 ✘（宕机，无所谓）
                            └──AppendEntries(entry, term5)──▶ F4 …（慢，无所谓）
                            ② 本地 + F1 + F2 = 3/5 多数派持久化
                               → commit（应用到状态机）→ 应答客户端成功
                            ③ 后续心跳携带最新 commitIndex（日志已提交到的位置），F1/F2/F4 跟进提交
```

与 2PC 的关系：**共识解决的是"提交决定"这一步的容错**——不再有可以单方面卡死全场的协调者，leader 宕机后多数派立刻选出新 leader 接着干，已 commit 的日志因为必然存在于多数派而不丢。很多系统在共识之上再跑跨分片事务（每个分片内部用 Raft/Paxos 复制）：

- **MySQL MGR（MySQL Group Replication，组复制）**：Paxos 变体（XCom）多数派确认每个事务（见 09 篇）；
- **etcd**：Raft，提供线性一致的 KV 与租约（常被用作集群仲裁）；
- **TiDB（TiKV）**：Multi-Raft，每个数据分片一组 Raft。

对开发者的意义：你直接写 Raft 的机会不多，但你选择"强一致的元数据/账务存储"时，底层就是这一层——理解"多数派 = 容错 + 写放大"（写放大：每笔写要多数派节点各自持久化一份日志），才能正确评估它的吞吐上限与部署形态（至少 3 副本、跨可用区部署）。

## 五、数据库内 vs 跨数据库：先问能不能单库

- **单库内多表**：一次本地事务天然原子——预写式日志（WAL，见 06 篇）是一条提交记录、一个提交点。这就是"能不分库就别分库"最硬的理由：**一致性成本为零**。
- **跨库/跨服务**：两台机器各有各的日志，没有共同提交点，才需要 2PC、共识或最终一致方案。
- **中间地带**：同库多表之间的并发冲突用锁与隔离级别解决（见 [./05-lock.md](./05-lock.md)、[./04-mvcc.md](./04-mvcc.md)），那是并发控制，不叫分布式事务。

判断顺序：能不能同库 → 能不能用消息解耦 → 实在不行才上 2PC/共识。每一级的成本都比上一级高一个量级。

## 六、业务侧最终一致（开发者最常用）

### 本地消息表 / outbox 模式（重点）

直觉：与其追求"同时"写库和发消息，不如把消息先塞进**同一个本地事务**里，发送这件事异步补做——原子性由最便宜的单库事务买单。

```text
┌─ 生产方（订单服务）────────────────────────────────────────┐
│ ① 单个本地事务：                                            │
│      INSERT INTO orders (...);                             │
│      INSERT INTO outbox (message_id, payload,              │
│                          status='PENDING') ...;            │
│    COMMIT;      ◀── 原子性：要么都在，要么都不在              │
│                                                            │
│ ② 投递器（同进程/独立进程）：轮询 status='PENDING'           │
│      → 发送到 MQ（带全局唯一 message_id）                    │
│      → UPDATE outbox SET status='SENT'                     │
│    （崩溃在"已发送、未标记"→ 重发 → 由消费端幂等吸收）         │
└──────────────────────┬─────────────────────────────────────┘
                       ▼  MQ（至少一次投递）
┌─ 消费方 ───────────────────────────────────────────────────┐
│ ③ INSERT 去重表（唯一索引；冲突 = 重复消息 → 直接 ACK）        │
│    同一本地事务处理业务 → 提交 → ACK                          │
│    失败 → 重试若干次 → 死信队列（人工/自动兜底）               │
└────────────────────────────────────────────────────────────┘
（ACK = 消费确认，告诉消息系统这条已处理完）
```

要点：发送与"标记 SENT"不是原子的，**正确性不依赖它们原子**——重复投递被消费端幂等吸收，漏投递被轮询兜底（PENDING 迟早重发）。两个工程细节：

- **顺序**：同一业务键的消息需要有序时，投递器要按业务键分组、组内按 outbox 主键顺序发送，MQ 端把同一键路由到同一分区；不分组并发投递时，"创建"可能晚于"取消"到达；
- **清理**：`SENT` 状态的历史消息要定期归档删除，否则 outbox 会自己长成新的巨型表，拖垮轮询查询。

变体：用 CDC 工具（如 Debezium）读 binlog/WAL 代替轮询，延迟更低且不给业务库加压力。

### 事务消息（RocketMQ 半消息）

顺序反过来：先把消息以**半消息**形式发到 broker（消费者不可见）→ 执行本地事务 → 再 commit/rollback 半消息；broker 未收到确认时定时**回查**生产者的本地事务状态。与 outbox 互为替代：事务消息把"暂存"责任放在 MQ，outbox 放在业务库。两者都需要消费端幂等。

### Saga：正向链 + 补偿链

长流程拆成 N 个本地事务 T1…Tn，每个配一个补偿动作 C1…Cn；第 k 步失败则反向执行 Ck…C1。铁律：

- **补偿必须幂等**——补偿本身可能被重试多次；
- **补偿必须可重试**——补偿失败自动重试 + 告警，否则流程永久卡死；
- **补偿是业务撤销，不是时光倒流**——已发出的短信收不回，补偿只能记账/发对冲事件；
- Saga **没有隔离性**：中间状态对外可见，必须用状态机 + 乐观锁挡住"读到半成品"的并发方。

### 幂等三件套

最终一致的世界里，重复投递是常态语义（至少一次），幂等是入场券。先说清为什么必须落在数据库层：应用层的"先查后写"判重在并发下有竞态——两个重试的消费实例同时查到"未处理"，然后都执行了一遍业务；而唯一索引与 `UPDATE ... WHERE status=...` 由数据库的行锁和唯一性约束裁决，同一时刻只有一个赢家。三件套：

1. **唯一业务键 + 唯一索引**——让数据库做最后一道防线，应用层判重都可能有并发窗口；
2. **状态机约束**——只允许合法状态迁移，非法迁移直接 0 行生效；
3. **去重表**——消费侧记录已处理的 message_id，唯一索引冲突即重复。

```sql
-- PostgreSQL 16：消费去重，先插去重表，冲突即重复
INSERT INTO consumed_messages (message_id, consumed_at)
VALUES ('order-123-pay', now())
ON CONFLICT (message_id) DO NOTHING;
-- 影响行数 = 1 → 首次，继续业务处理；= 0 → 重复消息，直接 ACK

-- MySQL 8.0：等价写法
INSERT IGNORE INTO consumed_messages (message_id, consumed_at)
VALUES ('order-123-pay', now());
-- affected rows = 0 表示重复

-- 状态机约束：只有 INIT 可推进到 PAID，重复回调/乱序事件天然被挡住
UPDATE orders SET status = 'PAID' WHERE order_id = 123 AND status = 'INIT';
-- affected rows = 0 → 已处理或不存在，直接返回成功
```

## 七、一致性层级速查表

| 层级 | 手段 | 保证 | 代价 | 适用 |
|---|---|---|---|---|
| 1 单库事务 | 本地 ACID | 强一致、不丢 | 最低（一次本地落盘） | 默认选择 |
| 2 单库 + 锁/隔离 | `SELECT FOR UPDATE`、MVCC 隔离级别 | 强一致 | 低-中（并发度下降） | 同库并发正确性 |
| 3 跨库强一致 | 2PC / 共识组复制 | 提交原子、多数派存活则不丢 | 两轮 RPC + 持锁；部署重 | 资金划拨、库存核销 |
| 4 最终一致 | outbox / 事务消息 / Saga | 不丢但可迟到（需幂等） | 中（异步化，延迟可观察） | 绝大多数跨服务事件 |
| 5 异步不保证 | 裸发 MQ、fire-and-forget | 可丢可重 | 最高（无保证） | 日志、指标、缓存失效类 |

选择原则：**资金/账务宁可同步慢也要层级 3；营销通知层级 4 完全够；任何层级 4 之上必须先解决幂等，否则重试即重复。** 从上往下每一级都是"用一致性换吞吐/可用性"，选哪个取决于这条业务路径写错/写丢的赔偿单价。

## 八、分布式 ID：分库分表后的第一道题

### 为什么自增主键不能用了

分库后每个实例都有自己的 `AUTO_INCREMENT` 计数器，两个库都会生成 `id=1001`，全局立即冲突。可以给每个库配不同步长/偏移（`auto_increment_increment` / `auto_increment_offset`），但容量规划僵化、扩容要重新规划段位，只适合实例数固定的场景。

### 方案对比

| 方案 | 有序性 | 长度 | 外部依赖 | 主要问题 |
|---|---|---|---|---|
| 雪花 Snowflake | 趋势递增（毫秒内有序） | 64 bit | 时钟、机器 ID 分配 | 时钟回拨；workerId（即位布局中的机器 ID）重复即全局 ID 重复 |
| 号段模式 | 趋势递增 | 64 bit | DB（弱依赖，双 buffer 缓解） | 重启浪费一段；号段服务仍是关键路径 |
| UUIDv4 | 无序 | 128 bit（122 bit 随机） | 无 | B+ 树随机插入 → 页分裂、写放大、缓存命中率差 |
| UUIDv7 / ULID | 时间前缀有序 | 128 bit | 无 | 索引体积是 bigint 两倍；部分旧生态不支持 |

### 雪花算法：64 bit 位布局

```text
 63       62                    22          12           0
 ┌───────┬────────────────────────┬───────────┬───────────┐
 │符号位=0│  时间戳（41 bit, 毫秒）  │ 机器ID(10) │ 序列号(12) │
 └───────┴────────────────────────┴───────────┴───────────┘
           约 69 年不重复            1024 个实例  每毫秒 4096 个/实例
 生成顺序：同一毫秒内序列号递增 → 跨毫秒时间戳递增 ⇒ 整体趋势递增
```

**时钟回拨**（NTP 校时把系统时间拨回去）是雪花的命门：同一毫秒被用两次，序列号重叠 → ID 重复。应对：

- 回拨幅度小（几毫秒）：自旋等待到时间追平；
- 回拨幅度大：拒绝发号并报警，或切换到备用 workerId；
- workerId 分配不能靠静态配置写死——两台机器配同一个 ID 就是静默全局重复，要用注册中心（etcd/ZooKeeper）租约分配或以 MAC + 进程号派生并在启动时校验。

### 号段模式：一次取一段

```sql
-- MySQL 8.0：号段模式核心（每个业务一行，一次 UPDATE 推进一个 step）
UPDATE id_segments SET max_id = max_id + step WHERE biz_tag = 'order';
SELECT max_id, step FROM id_segments WHERE biz_tag = 'order';
-- 应用拿到区间 (max_id - step, max_id] 在内存发号，DB 每段只被访问一次
```

双 buffer：当前段用到一半时异步预取下一段，DB 抖动时仍有存量可发，把对 DB 的强依赖降成弱依赖。代价：重启浪费未用完的段（只是空洞，不影响正确性）。

### 与索引的关系

两大库内置的 UUID 生成函数生成的主键都不友好：

```sql
-- PostgreSQL 16：内置生成的是 v4（随机、无序）
SELECT gen_random_uuid();   -- 如 0e2c1f0a-...；时间有序的 uuidv7() 要到 PG 18 才内置

-- MySQL 8.0：UUID() 返回 v1（含 MAC 地址与时间戳，但时间戳低位在前，同样不具索引友好性）
SELECT UUID();
```

主键有序 = 聚簇索引顺序追加，页写满才分裂新页；UUIDv4 随机主键 = 每次插入都可能落在中间页，触发页分裂与刷脏放大，缓冲池命中率同步劣化（详见 [./01-storage-engine.md](./01-storage-engine.md)、[./02-index.md](./02-index.md)）。所以"分布式 ID 选型"本质上是**写入路径的索引设计问题**，不只是"生成一个不重复的数"。

## 开发者清单

**该做：**

- 跨服务一致性先问"能不能放进同一个库"——同库单事务是最便宜的强一致，没有之一。
- 所有 MQ 消费者按"至少一次投递 + 幂等消费"设计——重试是常态语义，不是异常路径。
- outbox 消息带全局唯一 message_id 与业务键——没有唯一键支撑的幂等只是注释里的愿望。
- 每条跨服务链路写清失败矩阵（超时、部分成功、重复投递、消费方宕机）——没写过的路径就是未来的故障单。
- 分布式 ID 选型先算主键有序性对索引的影响——它直接决定写入放大与缓冲池命中率。

**不该做：**

- 不要用分布式事务包装器（XA/JTA）包住本来能单库提交的逻辑——两轮 RPC + 全程持锁的代价，多数业务路径承受不起。
- 不要相信 MQ 的"恰好一次"投递——主流 MQ 提供至少一次，消费端 ACK 丢失也会重投。
- 不要"先发消息再写库"或"先写库再裸发消息"——进程在两步之间崩溃，事件无声丢失，且无法追查。
- 不要让 Saga 补偿"试一次就放弃"——补偿失败必须可重试 + 告警，否则整条流程永久卡死。
- 不要静态写死雪花 workerId——两台机器同 ID 意味着静默的全局主键冲突。

## 常见误区

1. **"CAP 选了 AP 就永远放弃一致性。"** 取舍粒度是请求路径：同一系统内资金路径可以 CP、通知路径可以 AP，互不冲突。
2. **"最终一致性 = 没有保证。"** 它承诺停写后收敛，且可叠加单调读、读己之写等会话保证——语义是分层可选购的。
3. **"2PC 慢是数据库的锅。"** 主要损失在两轮 RPC、多次 fsync 与 prepare→commit 之间全程持锁；跨机房 RTT 才是数量级主因。
4. **"Raft 多数派 = 性能更好。"** 共识为容错付出写放大：每笔写要多数派确认，写吞吐上限仍卡在单 leader。
5. **"用了事务消息/outbox 就不用幂等了。"** 它们解决的是"发送与本地事务的原子性"，消费端重试与重复投递照旧发生，幂等一个都不能少。
6. **"UUID 当主键只是难看。"** 随机主键导致页分裂与缓存失效，高写入下吞吐可以差出数倍（幅度取决于页大小与负载分布）；UUIDv7/ULID 就是为此而生。

## 自测题

1. CAP 里 P 为什么不可选？
   （网络分区是分布式系统的常态；不选 P 等于只在网络完美时工作，等于没有分布式。）
2. 2PC 参与者在什么状态下持锁阻塞？谁能解除？
   （投了 yes 且未收到最终决定；只有协调者恢复并广播决定——或人工介入。）
3. 3PC 解决了 2PC 的哪个问题？为什么仍不安全？
   （用参与者超时消除了无限阻塞；网络分区下 abort 决定可能只送达部分参与者，未收到者超时默认提交，仍会不一致。）
4. 5 节点 Raft 集群最多容忍几台同时故障？为什么不是 3 台？
   （2 台；多数派 = 3，死 3 台后只剩 2 无法达成多数派，无法选出 leader 或提交。）
5. outbox 里"发 MQ"与"标记 SENT"不原子，为什么整体仍然正确？
   （重复发送由消费端唯一键幂等吸收；漏标记由轮询重发兜底；不丢不漏，只多投。）
6. 雪花 ID 时钟回拨 300ms，给出至少两种处理方式与代价。
   （自旋等待 300ms——尾延迟上升；拒绝发号报警——可用性下降；切备用 workerId——需要预分配。）
7. 为什么"能单库就单库"在一致性上几乎总是对的？
   （单库多表共享一个提交点和一份 WAL，原子性免费；跨库没有共同提交点，每一级替代方案都贵一个量级。）
8. 消费者处理成功但 ACK 前崩溃，消息会重投——你的系统哪一层挡住重复？
   （去重表唯一索引 / 状态机约束 / 唯一业务键，任一或组合，必须在数据库层兜底。）
