# 02 · 索引原理（Index Internals）

> 索引是"查询快"的来源，也是"写入慢"与"表变大"的来源——不理解它的工作机制，就只能在高频误建与不敢建之间摇摆。本篇讲清 B+ 树的结构与树高推导（为什么 3 层就能撑两千万行）、聚簇索引与回表的代价链路、最左前缀与索引失效的统一解释，以及各类索引的选型边界。01 篇的页与行格式是本篇的前置。

- 为什么 3~4 层 B+ 树就能支撑千万到亿级行？能自己推导吗？
- InnoDB 二级索引查整行的完整路径是什么？覆盖索引省掉了哪一段？
- 复合索引 (a,b,c) 对哪些 WHERE 形态有效？范围查询为什么"断"后续列？
- 常见索引失效各自的发生机制是什么？索引的写入代价和选择性怎么估？

## 一、为什么是 B+ 树：结构选型

### 直觉

索引的目的是把"逐行翻找"变成"按目录跳转"。目录结构要同时回答三个问题：一次跳转能跨多大范围（扇出，Fan-out）、跳几次能到数据（树高 = 页访问次数）、到了之后能不能顺着扫一段（范围扫描）。

| 结构 | 等值查找 | 范围扫描 | 查找路径长度 | 主要问题 |
| --- | --- | --- | --- | --- |
| 二叉 / 红黑树 | O(log n) 次节点访问 | 可但不连续 | n=100 万 → ~20 层 | 每个节点只有 2 个分叉，100 万行树高约 20 层，每层都是一次页访问 |
| 哈希表 | 平均 O(1) | 不支持 | 1 次定位 | 无法排序、无前缀、无范围；等值之外全废 |
| B 树 | O(log n) | 支持 | 中等 | 数据挤在内节点，键+数据同放，扇出被摊薄 |
| B+ 树 | O(log n) 且稳定 | 叶子链表顺序扫 | 千万行仅 ~3 层 | 内节点只放"键+指针"，扇出最大化；数据全在叶子 |

### 机制细节

- B+ 树的两个关键设计：**内节点只存键和子指针**（键是路牌，不是数据），所以单个 16KB 页能塞上千个分支；**所有数据都落在叶子层**，且叶子按键序串成双向链表，范围扫描退化为顺序读。
- 哈希不是不好，是"只解决等值"：`WHERE k = v` 一跳命中，但 `WHERE k > v`、`ORDER BY k`、`LIKE 'x%'`、最左前缀全部无能为力——第九节看它真正的用武之地。
- 树高为什么等于 I/O 次数的上界：每下降一层要访问一个页；根与上层内节点几乎总在缓冲池（08 篇），所以**真正落盘的往往只有最后的叶子页**。

### 对开发者的实际影响

- "索引快"不是魔法：它是"3 次页访问"对"全表 N 页顺序访问"的胜利。表越大，索引的相对优势越大；反过来，小表全表扫描可能更快（第六节）。

## 二、B+ 树长什么样：结构与查找过程

### 结构

```text
                       [ 根: 100 | 500 ]              ← 内节点：键是路牌，不存数据
                      /        |        \
              [10|50]       [200|300]      [700|900]  ← 内节点
              /  |  \       /   |   \      /   |   \
  ← 叶子 ⇄ [1 10 50] ⇄ [100 200 300] ⇄ [500 700 900] ⇄ 叶子 →
            数据/主键     数据/主键       数据/主键
  └────────── 叶子层：所有数据按键有序，双向链表 ──────────┘

  点查 300：根(100 ≤ 300 < 500 → 走中间分支) → 内节点(在 [200|300] 定位到含 300 的叶子) → 叶子页内二分：3 次页访问
  范围 [200, 700]：先定位到含 200 的叶子，沿链表向右扫到 700：1 次定位 + 顺序读
```

### 机制细节

- 页内查找不是逐条扫：InnoDB 靠 Page Directory 槽做二分（01 篇），PG 的 B-tree 页对索引元组做二分。
- 等值查找到叶子后可能命中 0 条、1 条或多条（非唯一索引），叶子内继续沿记录链比对。
- 范围查询的执行形态是"定位一次 + 顺序扫链表"，这也是 `ORDER BY 索引列`、`GROUP BY 索引列` 能免排序的原因——输出序就是索引序（07 篇展开）。
- 双向链表支撑反向扫描（`ORDER BY ... DESC`），InnoDB 8.0 之前"降序索引"只是解析了语法实际仍建升序，混合排序只能靠额外排序（第十节）。

### 对开发者的实际影响

- 深分页 `LIMIT 100000, 20` 慢的原因就在图里：沿链表扫过前 10 万行再丢掉——优化思路是"记住上次位置"的游标式分页（07 篇展开）。

## 三、树高推导：三层为什么能撑两千万行

### 直觉

"索引快"的核心不是比较次数少，而是**每层只花一次页访问**。扇出有多大，树就有多矮——这是能算出来的。

### 机制细节（完整计算）

以 InnoDB 16KB 页、BIGINT 主键为例，估算非叶节点的分支数：

- 每个目录项 = 键 8B + 子页指针 6B = 14B（忽略页头与记录头的少量开销，实际略低）。
- 每页可容纳 16384 ÷ 14 ≈ **1170** 个分支。
- 叶子层按行 1KB 估算，每页约 16 行。

```text
高度 1（仅根作叶子）:  16 行
高度 2:  1170 × 16                      ≈ 1.9 万行
高度 3:  1170 × 1170 × 16               ≈ 2190 万行   ← 千万级表的常态
高度 4:  1170 × 1170 × 1170 × 16        ≈ 256 亿行   ← 十亿级也才 4 层
```

三点修正，让数字贴近现实：

- 根和中间层几乎常驻缓冲池，3 层树的点查通常只有叶子那一次可能落盘。
- 主键换成 16B 的 UUID：目录项 22B → 每页约 745 分支；再叠加随机插入的 ~69% 页填充（01 篇第六节），高度 3 的容量从两千万级缩水到约千万级，更容易提前长到 4 层。
- PG 是 8KB 页、索引项还要加约 8B 元组头与 4B 行指针，内节点分支数降到数百，同样行数下树常比 InnoDB 高 1 层左右——多一层 = 缓冲池未命中时多读一个页，量级结论不变。

### 对开发者的实际影响

- "2000 万行表的点查 = 约 3 次页访问"应当成为本能；任何"这条索引查询为什么慢"的排查，先问是不是真的走到了叶子、走了几次。
- 反向推论同样成立：让树变高的不是行数本身，而是**页数**——宽行、随机键、低填充率都在偷偷加层。

## 四、聚簇索引、二级索引与回表

### 直觉

01 篇说过：InnoDB 表 = 主键 B+ 树（聚簇索引），叶子存整行；二级索引是另一棵树，叶子只存"索引列 + 主键值"。查完二级索引还差一步——拿着主键回主键树取整行，即回表（Bookmark Lookup）。

### 结构

```text
SELECT * FROM orders WHERE order_no = 'X1'   （order_no 为二级索引）

   idx_order_no 树                    主键 B+ 树（= 表本身，01 篇图）
        [根/内层]                          [根/内层]
            ↓ 下降 ~3 层                       ↓ 下降 ~3 层
   [叶子: X1 → id=88] ──── 回表 ───→  [叶子: id=88 + 整行]
                                           ↑
   若只 SELECT id, order_no（覆盖索引）→ 右半边整段不需要，直接返回
```

### 机制细节

- 代价链路：二级索引点查 = 两棵树各下降一次；两棵树的叶子都未命中缓冲池时，最多 3+3=6 次页访问，且第二段是随机读。单条无所谓，一秒一万条就是灾难。
- **覆盖索引（Covering Index）**：查询需要的列全部包含在索引里，就不用回表。MySQL 没有 `INCLUDE` 语法，靠把需要的列追加进复合索引实现；PostgreSQL 11+ 支持 `CREATE INDEX ... INCLUDE (列)`，把不参与定位、只用于输出的列挂在叶子，不增大内节点。
- PG 的二级索引叶子存 TID 直达堆页（01 篇），没有"二次树下降"，但"命中大量行时逐 TID 回堆"的随机读代价同样存在——覆盖索引（Index Only Scan）同样是 PG 的大杀器，还依赖可见性映射判断能否跳过堆访问（04 篇）。

| 能力 | MySQL 8.0 | PostgreSQL 16 |
| --- | --- | --- |
| 覆盖索引写法 | 复合索引带上输出列 | 复合索引，或 `INCLUDE` 挂输出列 |
| 只为部分行建索引 | 不支持 | `WHERE` 子句的部分索引 |
| 对表达式建索引 | 函数索引（8.0.13+） | 原生表达式索引 |
| 混合升降序索引 | 降序索引（8.0） | 列级 `ASC` / `DESC`，一直支持 |
| 计划里的覆盖确认 | `Extra: Using index` | `Index Only Scan` |

```sql
-- MySQL 8.0：用复合索引实现覆盖，避免回表
-- 查询：SELECT id, status FROM orders WHERE customer_id = 42;
CREATE INDEX idx_cust_status ON orders (customer_id, status);
-- EXPLAIN 的 Extra 出现 "Using index" 即覆盖成功

-- PostgreSQL 16：INCLUDE 把输出列挂到叶子，保持索引定位部分精瘦
CREATE INDEX idx_cust_inc ON orders (customer_id) INCLUDE (status);
-- PG 还有两种 MySQL 没有的形态：
CREATE INDEX idx_active ON orders (customer_id) WHERE status <> 'DONE';  -- 部分索引（Partial Index）
CREATE INDEX idx_email_lc ON customers (LOWER(email));                  -- 表达式索引（Expression Index）
```

### 对开发者的实际影响

- 高频路径上的查询，优先设计成"索引列定位 + 覆盖输出"两步，而不是习惯性 `SELECT *`。
- 部分索引适合"大表里只反复查一小撮"的场景（如未完成订单）：索引体积只和那部分行成正比。

## 五、最左前缀：复合索引的使用边界

### 直觉

复合索引 (a,b,c) 不是三个索引，是**一个**按 (a,b,c) 三元组整体排序的 B+ 树：先按 a 排，a 相同按 b，b 相同按 c。字典里查"第二个字母是 k 的单词"没法用目录——最左前缀（Leftmost Prefix）的一切规则都从这一句推出。

| WHERE 形态 | (a,b,c) 可用前缀 | 说明 |
| --- | --- | --- |
| `a = 1` | a | 最左列在 |
| `a = 1 AND b = 2` | a, b | 连续两列 |
| `a = 1 AND b = 2 AND c = 3` | a, b, c | 全部参与定位 |
| `b = 2`（无 a） | 无 | 缺最左列；MySQL 8.0.13+ 的跳扫（Skip Scan）在 a 取值很少时可救，别依赖 |
| `a = 1 AND c = 3` | 仅 a | c 不能跳过 b 参与树定位 |
| `a > 1 AND b = 2` | 仅 a | 范围列之后，b 退出树定位 |
| `a = 1 AND b LIKE 'x%'` | a, b | 前缀 LIKE 本质是范围 |
| `ORDER BY a, b`（配 `a =`） | a, b | 直接用索引序，免排序 |

### 机制细节

- "范围之后失效"的机制：对 a 做范围后，命中的叶子区间里 b 是乱序的（每个 a 值内部 b 各自成序），无法继续二分定位，只能逐行判断。
- 两个重要缓解：索引条件下推（Index Condition Pushdown, ICP）让"退出树定位的列"仍在存储引擎层用索引值先过滤，少回表（EXPLAIN 的 Extra 显示 `Using index condition`）；跳扫让首列取值极少时按每个取值各查一次——适用面窄，规划时当没有它。
- 列序经验法则：等值列在前、范围列在后；选择性高的在前（第八节）；排序/分组列尽量紧跟等值列。
- "ORDER BY 索引列免排序"同样受最左前缀约束：`ORDER BY b, c` 单独出现（无 a）用不上 (a,b,c) 的序。

### 对开发者的实际影响

- 建复合索引前，把该表的真实查询形态（等值/范围/排序列）列出来对齐一次，比事后靠"再加一个索引"补救便宜得多。

## 六、索引失效场景清单

以下每条都给机制，不给"背诵口诀"——机制记住了，新场景自己能判断。

MySQL 8.0 / PostgreSQL 16（逐条标注适用的数据库）：

1. **对索引列套函数或运算**：`WHERE YEAR(created_at) = 2024` 要对每行算函数才能比较，索引序帮不上忙（MySQL 与 PG 同）。改写成区间 `created_at >= '2024-01-01' AND created_at < '2025-01-01'`，或建函数/表达式索引（第十节、PG 原生支持）。
2. **隐式类型转换（MySQL）**：`WHERE phone = 13812345678` 而 phone 是 VARCHAR——MySQL 把**列**转成数字逐行比较，索引失效；写成 `'13812345678'` 即恢复。PG 方向相反：`int_col = '42'` 时转换发生在常量上，索引照用（`text_col = 42` 则直接报错）。细节见 18 篇。
3. **前导通配符**：`LIKE '%x'` / `LIKE '%x%'`——B+ 树只对前缀有序，无法定位起点；`LIKE 'x%'` 是范围，可用。真的要搜中缀：MySQL 用 FULLTEXT（中文需 ngram 解析器），PG 用 `pg_trgm` 扩展建 GIN/GiST 索引（第九节）。
4. **OR 混合无索引列**：`WHERE tenant_id = 1 OR memo = 'x'`（memo 无索引）——OR 的每一侧都要能独立走索引才可能用索引合并（index_merge）；一侧无索引就整体退化为全表扫描。早期 MySQL 版本对 OR 更保守，直接放弃索引。
5. **优化器理性弃索引**：预估命中行数占比大（经验上 20%~30% 以上，随行宽与缓冲池浮动）时，大量随机回表比顺序全表扫描更贵，优化器主动选全表扫。这不是"失效"，是正确决策——应对办法是覆盖索引，或接受全表扫。
6. **JOIN 两侧排序规则（Collation）不一致（MySQL）**：`utf8mb4_general_ci` 与 `utf8mb4_0900_ai_ci` 混用时比较需转换，某一侧索引用不上。建表统一字符集与排序规则（18 篇）。
7. **复合索引缺最左列**：即第五节的矩阵，列在这里是因为它是最常见的"失效"。

## 七、索引的代价：写入、空间与冗余

### 机制细节

- **写入**：每多一个索引，每次 INSERT / DELETE 都要额外维护一棵树（定位 + 可能的页分裂，01 篇第五节的写放大逐个上演）；UPDATE 只有改到索引列才动对应索引。InnoDB 二级索引的"改"实现为删旧插新。
- **空间**：二级索引的体积常与数据本身同量级——一张 20GB 的表带 5 个二级索引，索引合计再吃 10~20GB 很正常；InnoDB 还要再乘上每行复制的主键宽度（01 篇）。
- **冗余索引**：(a,b) 的前缀就是 a，能覆盖 (a) 的一切用途——独立的 (a) 是纯冗余（例外：(a) 承担唯一约束）。反向误区更常见：以为建了 (a) 就"顺便"支持 (a,b) 查询，其实完全不能。

```sql
-- MySQL 8.0：sys schema 自带冗余索引报告
SELECT * FROM sys.schema_redundant_indexes;

-- MySQL 8.0：删索引的安全姿势——先设为不可见（Invisible Index）
ALTER TABLE orders ALTER INDEX idx_old SET INVISIBLE;
-- 观察一段时间无性能回退后再：DROP INDEX idx_old ON orders;

-- PostgreSQL 16：没有不可见索引，删前先看使用统计（注意统计自上次重置起算）
SELECT relname, indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE relname = 'orders'
ORDER BY idx_scan;
```

### 对开发者的实际影响

- 索引是"用写放大换读加速"的合同：加索引前先确认对应查询的频率与收益，删索引前用不可见索引（MySQL）或使用统计（PG）兜底。
- PG 删索引没有灰度手段，把 `CREATE INDEX`（必要时 `CREATE INDEX CONCURRENTLY`）语句留档，回滚成本就是重建时间。

## 八、选择性：这个索引值不值得建

### 机制细节

- 选择性（Selectivity）= `COUNT(DISTINCT col) / COUNT(*)`，取值 0~1：越接近 1，一个值平均过滤掉的行越多，索引越值钱。
- 单列选择性低的典型是状态、性别、布尔列（选择性 2/N ≈ 0）：等值查询命中约一半行，第六节第 5 条会接管——大概率全表扫。
- 但"低选择性列"常能被**组合**救活：status 单看无用，(status, created_at) 对"某状态下最近订单"可能选择性极高。判断标准始终是"这个查询条件过滤后剩多少行"，不是单列选择性。

```sql
-- PostgreSQL 16（注意转 numeric，否则整数除法得 0）
SELECT COUNT(DISTINCT status)::numeric / NULLIF(COUNT(*), 0)      AS sel_status,
       COUNT(DISTINCT customer_id)::numeric / NULLIF(COUNT(*), 0) AS sel_customer
FROM orders;

-- MySQL 8.0（除法本身返回小数）
SELECT COUNT(DISTINCT status) / NULLIF(COUNT(*), 0)      AS sel_status,
       COUNT(DISTINCT customer_id) / NULLIF(COUNT(*), 0) AS sel_customer
FROM orders;
```

- 优化器做选择时用的也是这类统计（外加空值比例、相关性等），统计过期会导致选错索引——`ANALYZE`（PG）与自动统计（MySQL）的细节在 07 篇。

### 对开发者的实际影响

- 经验起点：单列选择性长期低于 ~10% 且没有组合场景，别建单列索引；反过来，外键列（tenant_id、user_id 这类）几乎永远值得建——它们是等值过滤与 JOIN 的主战场。

## 九、B+ 树之外：其他索引类型

| 类型 | 等值 | 范围/排序 | 典型场景 | 备注 |
| --- | --- | --- | --- | --- |
| B+ 树（两边默认） | 支持 | 支持 | 通用 | MySQL InnoDB 唯一的通用类型；PG 默认 |
| 哈希（Hash） | O(1) | 不支持 | 等值且键离散（如长随机 token） | PG 10+ 崩溃安全（记录 WAL），可在备库使用；不支持多列与唯一约束；InnoDB 的自适应哈希（Adaptive Hash Index）是引擎自动维护的内部结构，非用户索引（8.0 默认开启，8.4 起默认关闭） |
| GIN（PG） | 包含/相交 | 有限 | jsonb、数组、全文检索 | 倒排索引（Inverted Index）；`jsonb_path_ops` 更小但只支持 `@>`；写入维护重，有 fastupdate 合并机制 |
| GiST（PG） | 支持 | 支持（含 kNN 近邻） | 几何、范围类型（range）、地理 | 广义搜索树框架，具体语义由操作符类决定 |
| SP-GiST（PG） | 支持 | 有限 | 点、IP 前缀、radix 树场景 | 空间划分树（四叉树/基数树一类） |
| BRIN（PG） | 块级摘要 | 支持 | 超大表 + 物理顺序相关列 | 每 128 页（1MB）记一段 min/max；追加型表的 created_at 是教科书场景 |
| FULLTEXT（MySQL） | — | — | 全文检索 | InnoDB FULLTEXT；中文需 ngram 解析器 |

```sql
-- PostgreSQL 16：BRIN——日志型大表的 created_at，体积比 B+ 树小几个数量级
CREATE INDEX idx_events_created ON events USING brin (created_at);

-- PostgreSQL 16：GIN——jsonb 字段内的包含查询 WHERE payload @> '{"kind":"pay"}'
CREATE INDEX idx_payload ON events USING gin (payload jsonb_path_ops);

-- PostgreSQL 16：哈希索引——只做等值查的长随机 token
CREATE INDEX idx_token ON sessions USING hash (token);

-- MySQL 8.0：全文索引（中文用内置 ngram 解析器）
CREATE FULLTEXT INDEX ft_title ON articles (title) WITH PARSER ngram;
```

### 对开发者的实际影响

- BRIN 的适用前提是"物理顺序与列值相关"——自增/时间列的追加型表天然满足；频繁 UPDATE 打乱物理序的表则基本失效。
- GIN 换来的是"查询端支持 jsonb 内部条件"，付出的是写入维护与索引膨胀：只在确有查询模式时建。

## 十、MySQL 8.0 索引能力一览

- **函数索引（Functional Index，8.0.13+）**：对表达式建索引，破解第六节第 1 条失效。
- **不可见索引（Invisible Index，8.0）**：对优化器隐身但对写入照常维护，是删除索引前的灰度手段（第七节）。
- **降序索引（Descending Index，8.0）**：真正按 DESC 存储；5.7 只是解析语法实际仍建升序，混合序 `ORDER BY a ASC, b DESC` 在 8.0 才能靠索引免排序。

```sql
-- MySQL 8.0
CREATE INDEX idx_created_year ON orders ((YEAR(created_at)));        -- 函数索引
ALTER TABLE orders ALTER INDEX idx_old SET INVISIBLE;               -- 不可见索引（第七节）
CREATE INDEX idx_tenant_upd ON orders (tenant_id ASC, updated_at DESC);  -- 降序索引
```

## 十一、EXPLAIN 预告：怎么看索引有没有被用上

只列关键字段，逐字段精读与执行计划分析留给 07 篇：

```sql
-- MySQL 8.0：一眼判断索引使用情况
EXPLAIN SELECT id, status FROM orders
WHERE customer_id = 42 AND created_at >= '2026-08-01';
-- 关注：type 是否 ref/range，key 是否预期索引，
--       Extra 是否 Using index（覆盖）/ Using index condition（ICP）

-- PostgreSQL 16：看真实执行与页命中
EXPLAIN (ANALYZE, BUFFERS) SELECT id, status FROM orders
WHERE customer_id = 42 AND created_at >= '2026-08-01';
-- 关注：Index Scan / Index Only Scan / Bitmap Heap Scan，
--       Buffers: shared read 与 shared hit 的比例（08 篇）
```

- **type**（MySQL）：访问类型，从好到坏常见为 `const` / `eq_ref` / `ref` / `range` / `index`（扫整棵索引树）/ `ALL`（全表扫描）。
- **key / possible_keys**：实际选用与候选的索引；`possible_keys` 有而 `key` 为空 = 优化器弃用（回到第六节第 5 条想原因）。
- **rows**：预估行数，配合过滤条件看"预计回表多少行"。
- **Extra**：`Using index` = 覆盖索引；`Using index condition` = ICP；`Using filesort` / `Using temporary` = 额外排序或临时表（07/13 篇）。
- PG 对应地看 `EXPLAIN (ANALYZE, BUFFERS)`：`Index Scan` / `Index Only Scan` / `Bitmap Heap Scan` 与 `Buffers: shared hit/read` 的比例（08 篇展开）。

## 开发者清单

**该做：**

- 高频查询按"等值列在前、范围列在后、排序列跟上"设计复合索引——一套列序服务定位、过滤、排序三件事。
- 能覆盖就覆盖：把高频查询的输出列纳入索引（MySQL 进复合索引、PG 用 INCLUDE），消灭回表的随机读。
- 外键过滤列（tenant_id / user_id 一类）默认建索引——等值过滤与 JOIN 的主战场，选择性通常够高。
- 加索引前查选择性、删索引前查冗余与使用统计——两个动作都是一条 SQL 的事（第七、八节）。
- MySQL 删索引走"不可见 → 观察 → 删除"三步——回滚成本从重建索引降到一条 ALTER。
- 长随机 token 的纯等值查询，PG 可考虑哈希索引——比 B+ 树小且等值一跳。

**不该做：**

- 不要在索引列上套函数再比较——先改写成区间，确需表达式就建函数/表达式索引。
- 不要拿 VARCHAR 列和数字字面量比较（MySQL）——隐式转换让索引当场失效，这是线上事故的高发写法。
- 不要为低选择性列建单列索引（status / 性别 / 布尔）——大概率被优化器弃用，白付写入代价。
- 不要重复建 (a) 与 (a,b)——(a) 是纯冗余，除非它承担唯一约束。
- 不要用前导通配符 LIKE 做搜索功能的实现——那不是索引问题，是需求要用全文/倒排方案。
- 不要看到 `type=ALL` 就认定是 bug——大比例回表时全表扫描是理性选择，先确认过滤比例。

## 常见误区

1. **"索引越多越好。"** 每个索引都是一份写入放大 + 存储副本 + 优化器的候选负担；高频写、低频查的表上乱建索引是负资产（第七节）。
2. **"走了索引就一定快。"** 走二级索引但命中 30% 行数时，随机回表比顺序全表扫更慢——优化器弃索引往往是对的，问题是你的查询本身该换形态（覆盖或分批）。
3. **"建了 (a,b) 就等于也有 (b)。"** 方向反了：(a,b) 能覆盖 a 的查询，覆盖不了 b 的——最左前缀只认左边（第五节矩阵）。
4. **"哈希索引 O(1)，全面优于 B+ 树。"** 哈希只做等值：范围、排序、前缀、最左前缀全部不支持；且 PG 哈希索引不支持多列与唯一约束。
5. **"函数失效是 MySQL 的怪癖。"** 两家一样：对列做函数/运算后，索引序都无法利用；PG 的解法（表达式索引）只是更顺手，不是机制不同。
6. **"慢查询加个索引就能救。"** 先看 EXPLAIN 确认瓶颈是不是缺索引——还有统计过期、隐式转换、深分页、回表比例过大等多种病因，加错索引只会同时拖慢写入。

## 自测题

1. B+ 树叶子层为什么必须是双向链表？只单向行不行？
   （范围扫描要向右扫；`ORDER BY DESC` 与反向扫描需要向左——单向链表会废掉一半范围场景。）
2. 默认 16KB 页的 InnoDB，BIGINT 主键、行 1KB，3 层树大约能存多少行？写出推导。
   （16384/14 ≈ 1170 分支；1170² × 16 ≈ 2190 万行。）
3. InnoDB 二级索引 `idx_email` 点查整行，最坏要访问多少个页？覆盖索引后呢？
   （两棵 3 层树各下降一次，最坏 3+3=6 页；覆盖后只走二级树，最坏 3 页。）
4. `WHERE a = 1 AND b > 10 AND c = 3`，索引 (a,b,c) 各列的参与情况？
   （a、b 参与树定位；b 是范围列，c 退出定位但可被 ICP 在索引层过滤。）
5. 为什么 `LIKE '%x'` 用不上 B+ 树索引，`LIKE 'x%'` 可以？
   （索引只按前缀有序：给定前缀能定位起点区间；前导通配符意味着任意起点，等于全扫。）
6. status 列只有 3 个取值，(status, created_at) 复合索引为什么可能仍然高效？
   （等值 status + 范围 created_at 连续两列参与定位，"某状态下时间段内"的过滤后行数少；单列选择性不等于查询选择性。）
7. MySQL 删索引前为什么先 `SET INVISIBLE`？这一步期间写入路径有变化吗？
   （灰度观察优化器是否真的不用它，避免误删导致回退；没有——不可见索引照常维护，只是优化器看不见。）
8. PG 的 BRIN 索引为什么可以比 B+ 树小几个数量级？代价是什么？
   （每 128 页只存一段 min/max 摘要而非每行一个条目；只能定位到块区间，物理顺序与列值不相关时几乎过滤不掉任何块。）
