# 性能测试报告：HTTP 层 Hono → keala 迁移 A/B 对照（2026-09-01，v2 · keala 0.6.1 复测）

> 被测对象：Tillgate @ `main`（Hono 4.13 基线，worktree 独立检出）
> vs `refactor/hono-to-keala` 分支（keala **0.6.1**，npm 引入；升级提交 `66171ed`）。
> 两端业务代码同源（分支仅替换 HTTP 框架层与配套装置），所有差异可归因于框架。
> v1（同日上午，keala 0.5.1）数据保留于 §6 作对照；0.5.1→0.6.1 的同刻三角归因见 §5.1。
> 原始采样：v2 于 `/tmp/bench-results/rerun-0.6.1/`（results/*.json + logs/ + 三角数据）。

---

## 1. 测试目的

量化「Hono → keala」HTTP 层迁移在四个层面的实际收益与代价：
框架层微基准（探针/JSON body）、真实网关全链路（非流式/流式）、持续饱和
（吞吐/尾延迟/内存收敛）、冷启动；并单独量化 **keala 0.5.1 → 0.6.1 升级**
（上游 dogfood R2：body 快路径 + r8 修复）带来的变化。给出运维参数建议与上游改进项。

## 2. 被测对象

| | 基线（Hono 版） | 被测（keala 版 v2） | 升级前对照（v1） |
|---|---|---|---|
| 代码 | main @ `b0709a1` | refactor/hono-to-keala @ `66171ed` | 同分支 @ `0cd2db8` |
| HTTP 框架 | hono 4.13.x | **keala 0.6.1**（npm，零依赖） | keala 0.5.1 |
| 运行时/装配 | bun 1.4 + 全真装配（PG/Redis/mock 上游，两端同款） | 同左 | 同左 |

## 3. 测试环境

- 硬件/系统：Apple Silicon（arm64），macOS darwin 25.5.0；同日两场会话（上午 v1 / 下午 v2）
- 数据面：本机 PostgreSQL（e2e 隔离 schema，全迁移链回放）+ 共享 Redis + mock 上游
  （openai-compatible，auto 脚本；kit 世界自带，每端独立实例）
- 负载工具：autocannon（bun 运行时）；SSE/冷启动为脚本自测
- 限流口径：两端同配关闭（`GLOBAL_RPM`/`PREAUTH_IP_RPM`/`ADMISSION_MAX_PENDING`/
  `ADMISSION_MAX_OLDEST_MS` 放大 + 渠道 rpm_limit 放大 + 路由策略单渠道直连）——
  测框架与装配面吞吐，不测限流闸与资损防线
- v2 装置口径修正（相对 v1，影响复现见 §8）：每轮 run 前复位共享 Redis 推理健康键；
  清理当日失败运行遗留的 1.8GB/2.1 万关系孤儿 e2e schema

## 4. 方法论与口径

- **ABAB 交替轮转**：两端服务常驻，逐轮轮换先后顺序（消顺序偏差）；每场景独立
  warmup（不计入）；每场景 6 轮（微基准 4~6 轮、SSE 3 轮、冷启动 3 次），取**中位数**。
- 饱和：200 连接 × 600s 打 `/livez`（两端顺序执行），10s 间隔进程树 RSS 采样。
- **同刻三角**（v2 新增）：hono(main) / keala 0.5.1 / keala 0.6.1 三端同机同分钟
  轮转对打——0.5.1→0.6.1 的差异以此为归因依据，不受会话间环境漂移影响。
- **已知局限**：
  1. localhost 极端压力，真实 LLM 网关业务流量为几十~几百 RPS 量级；
  2. 全链场景两端 non2xx=0 是数据采信前置条件（v2 三场全链均已达成）；
  3. 会话间绝对值漂移显著（hono 微基准上午 130.7k → 下午 162.3k RPS，+24%），
     **跨会话只比方向与同刻比值，不比绝对值**；
  4. 全链绝对吞吐受当日共享 PG/Redis 状态影响（见 §5.2 注），配对比率有效。

## 5. 测试结果（v2 · keala 0.6.1）

### 5.1 框架层微基准 + 同刻三角（c=50×8s×4 轮中位，三端同机同刻）

| 端 | GET /livez | POST /v1/echo（JSON 解析回显） |
|---|---|---|
| hono(main) | 162.3k RPS | 140.9k RPS |
| keala 0.5.1 | 150.9k RPS（0.930x） | 59.7k RPS（**0.424x**） |
| keala 0.6.1 | 148.4k RPS（0.914x） | 110.5k RPS（**0.785x**） |
| keala 0.6.1 无 bodyParser 插件层（诊断） | 149.0k RPS | —（facade 依赖插件） |

- **0.5.1 → 0.6.1 echo +85% RPS**（59.7k → 110.5k）：上游 `readBodyLimited`
  declared-length 原生 `arrayBuffer()` 单发读快路径（DOGFOOD-R2 C1）兑现；
  对 hono 差距从 −57.6% 收窄到 −21.5%。剩余差距为有界读取设计（413 预算 +
  记忆化 + 双 promise 结构）的固有成本——上游已裁决否决「json 委托 raw.json()」。
- livez 两版本持平（150.9k vs 148.4k）；**插件层零成本**（148.4k vs 149.0k，噪声内）。
- 上午 v1 的 livez「keala +13.6%」在下午不可复现（hono 自身绝对值日间 +24%），
  v2 口径下探针稳定为 keala −7~−9%。

### 5.2 真实网关（全真装配，两端同款隔离世界）

| 场景 | Hono | keala 0.6.1 | 比值 | p50/p99 |
|---|---|---|---|---|
| GET /livez（装配探针，c=50×10s×6 轮） | 48.1k RPS | 45.2k RPS | **−6.1%** | 4/6 vs 4/6ms |
| POST /v1/chat/completions 非流式全链（c=10×10s×6 轮；鉴权+目录+限流预占+计费+mock 上游+日志） | 236~275 RPS | 262~287 RPS | **+11.0% / +15.9%**（两场） | 24/56 vs 23/53ms（r1） |
| 同上 · keala **0.5.1** 同刻对照（12:55，同环境） | 275 RPS | 287 RPS | +4.4% | 105 vs 107ms（p99，含世界劣化） |
| SSE 流式（TTFT 首字节，10 流×3 轮） | ttft p50 31.4ms | ttft p50 29.5ms | **略优（−6%）** | 总时长 p50 52.9 vs 52.0ms |

- 全链两端 non2xx=0、SSE 坏流 0。
- **0.6.1 相对 0.5.1 在全链净赚约 +7~11 个百分点**（+4.4% → +11~16%），
  与微基准三角方向一致（body 解析是 chat 每请求路径的组成部分）。
- 注：全链绝对值显著低于上午 v1（2208 RPS），原因是当日环境而非框架——
  两端同付的每请求业务成本上升（billing 积压准入的 inventory 查询随 pending
  增长、共享 PG 当日写入累积）+ 世界随轮次单调劣化（r1 ~380 → r6 ~190 RPS，
  v1 的陈旧世界复跑同样落在 ~500 RPS 档）。**配对比率与同刻对照为有效口径。**

### 5.3 持续饱和（200 连接 × 600s，/livez，两端顺序执行）

| | Hono | keala 0.6.1 | v1（keala 0.5.1） |
|---|---|---|---|
| 均值吞吐 | 48,060 RPS | 45,188 RPS（**−6.0%**） | 41,399 RPS（−10.5%） |
| p50 / p99 | 4 / 6ms | 4 / 6ms（**完全平价**） | 4 / 9ms（+2ms） |
| 错误 / non2xx | 0 / 0 | 0 / 0 | 0 / 0 |
| RSS 曲线 | 535 → 543MB（60 样本，硬收敛） | 563 → 577MB（60 样本，硬收敛） | 886~887MB 平台 |
| 对基线内存比 | — | **+5.6%** | +106%（2.06x） |

- 0.6.1（含 r8 修复随版发布）把饱和内存平台从 2.06 倍压到 **1.056 倍**、
  p99 尾延迟从 +2ms 拉平、吞吐差距从 −10.5% 收窄到 −6.0%；两端曲线均无
  无界增长（末 30 样本漂移 <1%）。

### 5.4 冷启动（进程起 → 就绪，3 次/端中位；含 vitest 启动 + 隔离世界迁移回放）

| | Hono | keala 0.6.1 |
|---|---|---|
| wall 中位 | 1,245ms | 1,291ms（**平价**，单次区间重叠） |
| 进程内装配（世界+网关 ready） | 273ms | 274ms（平价） |

（v2 未采到启动后 RSS——冷启动形态进程即退；内存结论以 §5.3 饱和平台为准。）

## 6. v1 首测数据（同日上午，keala 0.5.1，保留对照）

| 场景 | Hono | keala 0.5.1 | 比值 |
|---|---|---|---|
| 微基准 livez / echo | 130.7k / 118.8k | 148.5k / 57.5k | +13.6% / **−51.6%** |
| 装配探针 /livez | 47.7k | 44.5k | −6.7% |
| 非流式全链（新鲜世界） | 2,208 RPS | 2,269 RPS | +2.7% |
| 陈旧世界全链（复跑首轮，参考） | 456 RPS | 590 RPS | +30% |
| SSE TTFT p50 | 15ms | 15ms | 平价 |
| 饱和吞吐 / p99 | 46,272 / 7ms | 41,399 / 9ms | −10.5% / +2ms |
| 饱和 RSS | 410~446MB 振荡带 | 886~887MB 硬平台 | ~2x |
| 冷启动 | 1,411ms | 1,413ms | 平价 |

归因诊断（v1 期）：echo 回归 100% 位于 `createBodyParser` facade 的
「字节缓冲 → UTF-8 解码 → JSON.parse」读取路径（换原生 `raw.json()` 诊断
130.1k RPS 反超）；该结论推动上游 0.6.1 快路径（§5.1 已兑现）。

## 7. 结论

1. **业务路径优势扩大**：非流式全链 +11~16%（v1 为 +2.7%），SSE 首字节略优
   （−6%）、总时长平价。网关真实成本在上游 IO 与计费链，0.6.1 的 body 快路径
   在每请求 JSON 解析上继续兑现收益。
2. **探针路径稳定小幅劣势**：微基准 −7~−9%、装配探针 −6.1%、长饱和 −6.0%，
   p99 已完全拉平（4/6 vs 4/6ms）。对 LB 探活无实际影响；纯转发型高 QPS
   小响应负载有 ~6% 量级劣势。
3. **JSON body 读取回归大幅收窄但仍存在**：微基准 −21.5%（v1 −51.6%）。
   剩余差距是有界读取（413 预算）设计成本，上游已裁决不 delegate——为安全语义
   接受该成本。
4. **内存问题实质解决**：饱和平台 572MB，仅比 Hono 基线高 5.6%（v1 为 2.06 倍）；
   曲线硬收敛无增长。
5. **质量面**：升级后根四门全绿（typecheck/lint 0-0/test/build）；e2e 默认门
   与双形态冒烟结论随 v1 收口不变（框架层仅错误判别从 message 正则改为 code 契约）。

## 8. 运维建议

| 对象 | 建议 |
|---|---|
| keala 版 gateway 容器内存 limit | **1.5GB**（0.6.1 饱和平台 572MB × 2.5 余量；v1 按 887MB 给的 2GB 可回收） |
| 容量规划 | 探针口径单核 ~34k RPS（Hono 36k）；业务路径由上游时长主导，网关层余量充足且优于基线 |
| 升级窗口 | **已完成**（0.6.1）；后续上游若落地路径作用域 use / 注册面泛型，适配层可再瘦身 |

## 9. 复跑要点（v2 装置）

- 基线：`git worktree add /tmp/tillgate-main main`（e2e 依赖 `@hono/node-server`
  为未声明依赖，需自 .bun store 补链到 apps/gateway/node_modules）。
- 被测：`refactor/hono-to-keala` @ `66171ed`（keala ^0.6.1）；0.5.1 同时刻对照
  用 `0cd2db8` 建 worktree。
- 装置：e2e kit 起全真装配（临时 bench-server.test.ts + 专用 vitest 配置，跑完即删）；
  环境键放大 `GLOBAL_RPM`/`PREAUTH_IP_RPM`/`ADMISSION_MAX_PENDING`/
  `ADMISSION_MAX_OLDEST_MS`/`DB_POOL_MAX`；路由策略改单渠道直连
  （`update routing_policies set policy='{"version":1,"enabled":false}'`）+
  渠道 `rpm_limit` 放大。
- **三个必须的装置防线**（v2 踩坑记录，缺一则全链数据被污染）：
  1. `retargetUpstream` 的 protocol 合法值是 `openai-compatible`（写成 `openai`
     会以 `unsupported_protocol` 全量 502）；直接用 `world.upstream`（kit 已按
     正确协议种好）则无需 retarget；
  2. 共享 Redis 的推理健康键（`inference:health:*`：死模型按真实模型名、渠道惩罚
     按渠道 id 命名）跨隔离世界碰撞——重试掩盖型失败 3 连击即把全局键打死、
     两端瞬时 `no_available_channel` 风暴；每轮 run 前 `DEL` 复位；
  3. 结算积压准入缺省 1 万张 pending 即关闸（`billing.settlement_backlog`），
     500+ RPS 轰炸 20s 触发——必须放大 `ADMISSION_MAX_PENDING`。
- 原始数据：v2 `/tmp/bench-results/rerun-0.6.1/`（各阶段 json + 三角 + 日志）；
  v1 `/tmp/bench-results/`（results.json + 阶段日志）。

## 10. 与预算（DESIGN §5）对照（v2 口径）

| 预算项 | 实测 | 判定 |
|---|---|---|
| 真实路径吞吐不低于基线 ±5% | 全链 +11~16%（同刻 0.5.1 对照 +4.4%） | ✅ |
| p99 不劣化超噪声带 | 全链/SSE/饱和 p99 全部持平或更优 | ✅ |
| 空闲 RSS 与饱和平台 ≤ 基线 +10% | 饱和平台 +5.6% | ✅（v1 ❌ → v2 ✅） |
| 冷启动不劣化 | 1291 vs 1245ms（区间重叠） | ✅ |

> 结论：0.6.1 升级后，迁移在业务面、尾延迟、内存、冷启动四项预算全部达标；
> 探针吞吐（−6%）仍在预算带内（±5% + 噪声），唯一保留的框架级差距是 body
> facade 微基准 −21.5%（安全设计成本，上游已裁决）。
